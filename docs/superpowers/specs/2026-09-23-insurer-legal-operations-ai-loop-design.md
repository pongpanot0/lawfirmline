# วงจร Legal AI และ Operations AI สำหรับสำนักงานคดีประกันภัย

**สถานะ:** รอตรวจแบบก่อนวางแผน implementation  
**ผู้ใช้หลัก:** เจ้าของสำนักงาน, ทนายผู้ดูแลคดี, ผู้ประสานงานรับเรื่อง  
**คำสัญญาผลิตภัณฑ์:** ลดการกรอกและตามงานซ้ำ พร้อมทำให้เรื่องที่ค้างมีเจ้าของและขั้นถัดไป โดยทนายยังยืนยันข้อเท็จจริงและการตัดสินใจสำคัญ

## สิ่งที่มีอยู่แล้ว

- หน้า Intake ขอ AI จัดประเภทเอกสาร มีข้อความอ้างอิงจากเอกสาร และให้ผู้ใช้ยืนยันผลผ่าน checklist
- `IntakeDocumentRequest` เก็บเอกสารที่ขอ สถานะ วันขอ วันได้รับ และไฟล์ที่ผูกไว้
- Intake มีงานของตัวเอง และงานจะย้ายไปอยู่กับ Case เมื่อแปลงเป็นคดี
- Court Day บันทึกผลนัดแบบ transaction และสร้างนัดถัดไป งานติดตาม ค่าใช้จ่าย หรือร่าง closing report ตามที่ผู้ใช้เลือก
- Action Center และหน้า Operations มีคิว งานค้าง workload, SLA และ performance อยู่แล้ว
- ค่า average turnaround ของ task ปัจจุบันคำนวณจาก `updatedAt - createdAt` เพราะ Task ไม่มีเวลาปิดงานโดยตรง จึงคลาดเคลื่อนได้เมื่อแก้ task หลังปิด

## แนวทางที่พิจารณา

1. **สร้าง Operations AI assistant แยกใหม่:** ยืดหยุ่น แต่ซ้ำกับ Intake, Court Day, Task และ Operations ที่มีอยู่ และเพิ่มค่าใช้จ่าย/ข้อมูลที่ต้องส่งให้โมเดล
2. **เชื่อมข้อมูลและการยืนยันเข้ากับ workflow เดิม (แนะนำ):** ให้ผล Legal AI ที่ทนายยืนยันแล้วเดินต่อเป็นสถานะเอกสาร งานในคิว ร่างรายงาน และตัวชี้วัด ใช้ UI เดิมและไม่มีการสร้างงานซ้ำ
3. **เพิ่มหน้า metrics อย่างเดียว:** ทำง่ายกว่า แต่ยังปล่อยให้เอกสารที่ขอและขั้นถัดไปหลุดระหว่างทีม

## แบบที่เสนอ

### 1. Intake: จากเอกสารที่ AI พบ ไปสู่คิวติดตาม

1. คงการจำแนกเอกสารและการยืนยันผลเดิมไว้ พร้อมแสดง source excerpt ก่อนบันทึก
2. เมื่อผู้ใช้ยืนยันเอกสาร ให้เลือกได้ว่าจะผูกไฟล์นั้นกับ `IntakeDocumentRequest` รายการใด หากมีรายการเดียวที่ชื่อตรงกันให้เสนอเป็นตัวเลือก; ถ้ามีหลายรายการต้องให้ผู้ใช้เลือกรายการก่อน
3. เมื่อยืนยันการผูกไฟล์ ให้บันทึก `documentId` และ `receivedAt` ใน request เดิม หากไม่มีรายการที่ตรง ให้บันทึก checklist อย่างเดียวและไม่เดาสถานะ
4. ส่ง request ที่ยัง `REQUESTED` หรือ `MISSING` ทุกระดับความจำเป็นเข้า Action Center เป็นรายการประเภทเอกสาร พร้อมชื่อ Intake, ผู้ดูแลติดตาม, วันครบกำหนด, ป้าย required/optional และลิงก์ตรงไปยัง Intake
5. ใช้ `IntakeDocumentRequest` เป็นแหล่งงานติดตามเอกสาร ไม่สร้าง Task ซ้ำโดยอัตโนมัติ งานที่คนสร้างเองยังใช้ `IntakeTasksPanel` และไหลต่อไป Case ได้ตามเดิม

### 2. หลังขึ้นศาล: แยกผู้รับรายงานให้ตรงกับบทบาท

คง flow ปิดนัดเดิมไว้ ไม่สร้าง Task หรือนัดซ้ำ เมื่อเป็นคดีที่มีบริษัทประกันเป็นผู้จ้าง/ผู้จ่ายเงิน ให้เพิ่มทางเลือกสร้าง **ร่างรายงานถึงลูกค้า/บริษัทประกัน** จากผลนัดที่ทนายบันทึกและข้อมูลนัดถัดไปที่ยืนยันแล้ว

- แสดงผู้รับเป็นลูกค้า/ผู้จ่ายเงินจาก `CaseCustomer` แยกจากลูกความ/ผู้เอาประกันจาก `CaseClient`
- เพิ่มประเภทผู้รับ (`CLIENT` หรือ `CUSTOMER`) และผูกกับบุคคล/บริษัทที่เลือกใน closing draft; ร่างเดิมถือเป็น `CLIENT` เพื่อคงความหมายเดิม
- ให้ทนายแก้ไขและอนุมัติได้ตาม flow เดิม การอนุมัติยังไม่ส่งอีเมล และไม่มีการส่งข้อความภายนอกอัตโนมัติ
- ร่างที่รอตรวจปรากฏใน Action Center เพื่อไม่ให้ค้างหลังปิดนัด
- หากไม่มีผู้จ่ายเงินหรือมีหลายรายโดยยังไม่เลือก ห้ามเดาผู้รับ ให้ผู้ใช้เลือกก่อนสร้างร่าง

### 3. Operations metrics ที่เชื่อถือได้

หน้า Operations แสดงสรุประดับสำนักงาน ไม่ใช่ leaderboard โดยใช้เฉพาะเหตุการณ์ที่มี timestamp จริง:

- Intake ถึงเปิดเป็น Case: `receivedDate` → `Case.openedAt`
- เวลาติดตามเอกสารที่ได้รับ: `requestedAt` → `receivedAt`
- เวลาปิดบันทึกผลนัด: เวลาเริ่มนัด → `CourtDay.completedAt`
- task turnaround สำหรับ task ใหม่: เพิ่ม `Task.completedAt` และกำหนดเมื่อเปลี่ยนเป็น `DONE`; ล้างเมื่อเปิดงานกลับมา
- จำนวนเอกสารที่ยังขาดและรายการติดตามเกินกำหนด

ไม่เรียกค่าเหล่านี้ว่า “เวลาที่ประหยัดได้” จนกว่าจะมี baseline ก่อนใช้งานและเปรียบเทียบกับช่วงนำร่อง งานเก่าที่ไม่มี `completedAt` คงเป็น `null` และไม่นำมาคำนวณ turnaround แทนการเดาเวลาปิดย้อนหลัง

## การทำงานของ AI และสิทธิ์ควบคุม

- ใช้ AI เฉพาะงานกับข้อมูลไม่เป็นโครงสร้างที่มีอยู่ เช่น จัดประเภทเอกสารและเสนอ match พร้อมหลักฐาน
- ใช้สถานะ request, วันกำหนด, ผู้ติดตาม และ SOP ของสำนักงานเป็นกฎสำหรับจัดคิวและแสดงขั้นถัดไป ไม่เพิ่ม external model call ในรอบนี้
- แยกบริษัทประกัน/ผู้จ่ายเงินออกจากผู้เอาประกัน/ลูกความทุกจุด
- ทุก write ที่เปลี่ยนสถานะเอกสาร สร้าง/แก้ร่าง หรือมอบงานต้องเกิดหลังผู้ใช้เห็นสิ่งที่จะเปลี่ยนและยืนยัน
- ทุก query ต้องใช้ firm scope และสิทธิ์เดิมของ Case/Intake; การอ่านคิวไม่สร้างหรือแก้ข้อมูล

## เกณฑ์รับงาน

1. ยืนยัน AI match แล้วเอกสารที่ผูกและสถานะ request ตรงกัน; ไม่มีการ mark received จากการเสนอของ AI เพียงอย่างเดียว
2. request ที่ยังขาดและถึงรอบติดตามปรากฏในคิวพร้อมเจ้าของ/กำหนดที่ถูกต้อง และเปิดไปยัง Intake ต้นทางได้
3. การโหลดซ้ำหรือ retry ไม่สร้าง task หรือร่างซ้ำ
4. ปิดนัดแล้วร่างรายงานแสดงผู้รับที่เลือกจากฝั่งลูกค้า/ผู้จ่ายเงิน แยกจากลูกความ และไม่มีการส่งออกเอง
5. สรุป Operations แสดงขอบเขตเวลาและจำนวนตัวอย่าง; ประวัติที่ไม่มี timestamp แสดงเป็นข้อมูลไม่พอ ไม่คำนวณทดแทน
6. ข้อมูลและปุ่มยืนยันทำงานได้ตามสิทธิ์ firm/role และรองรับทั้งภาษาไทยกับอังกฤษ

## ขอบเขตที่ไม่ทำ

- ไม่เพิ่มแชต AI กลางหรือหน้าควบคุมใหม่
- ไม่ให้ AI ตัดสินคดี ยืนยันข้อเท็จจริง มอบหมายงาน ส่งอีเมล หรือลบหลักฐานเอง
- ไม่กล่าวอ้างจำนวนชั่วโมงที่ประหยัดได้จากข้อมูลที่ไม่มี baseline
- ไม่เปลี่ยนขั้นตอนสร้าง Case หรือความหมายลูกค้า/ลูกความที่มีอยู่
