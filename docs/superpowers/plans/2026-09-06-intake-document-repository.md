# Intake Document Repository Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give Intake the same managed-document capability Case already has (versioned files, client-visibility toggle, download) by making `Document.caseId` nullable and adding a nullable `Document.intakeId`, as a system genuinely parallel to — not a replacement for — the already-shipped `IntakeAttachment` (which keeps feeding the AI precedent-analysis flow unchanged).

**Architecture:** `Document` gains a nullable `intakeId` alongside a now-nullable `caseId`, guarded by a DB `CHECK` constraint (exactly one must be set). `DocumentsService` gains five sibling methods (`findByIntake`, `uploadForIntake`, `uploadNewVersionForIntake`, `updateVisibilityForIntake`, `getFilePathForIntake`) that mirror the existing case-scoped ones. A new `IntakeDocumentsController` mounts them at `intake/:intakeId/documents`, firm-scoped in the service layer (matching how every other intake sub-resource is scoped — this codebase has no `IntakeAccessGuard`). `IntakeService.convertToCase()` gets one `updateMany` that re-points converted documents from the intake to the destination case.

**Tech Stack:** NestJS + Prisma (Postgres) backend (`apps/api`), Next.js/React frontend (`apps/web`), Jest for tests.

**Spec:** `docs/superpowers/specs/2026-09-06-intake-document-repository.md`

## Global Constraints

- Do not touch `IntakeAttachment`, `intake-precedent-analysis.service.ts`, or the AI-analysis button — those keep using `IntakeAttachment` exactly as they do today.
- Do not expose `visibleToClient` in any `(client-portal)` route or page.
- `documents.service.ts`'s existing case-scoped methods (`findByCase`, `verifyDocument`, `upload`, `uploadNewVersion`, `getFilePath`, `updateVisibility`) must keep their exact current signatures and behavior — only add new sibling methods, never modify the existing ones' logic (beyond what nullability of `caseId` in the schema forces, which is nothing, since they always pass an explicit `caseId` in their `where` filters).

## Relationship to `2026-09-06-intake-process-variations`

Independent of that plan — implement in either order. If that plan has already landed, `convertToCase()` will have two branches (create-new-case, attach-to-existing-case); Task 4 below touches both. If it hasn't landed yet, `convertToCase()` has only the create-new-case branch; Task 4 only touches that one (its Step 1 tells you how to check which shape you have).

Create `apps/api/src/documents/intake-documents.controller.ts`:

```typescript
import {
  Controller,
  Get,
  Post,
  Patch,
  Param,
  Body,
  UseGuards,
  UseInterceptors,
  UploadedFile,
  Res,
  Query,
} from '@nestjs/common';
import { FileInterceptor } from '@nestjs/platform-express';
import { Response } from 'express';
import * as fs from 'fs';
import { DocumentsService } from './documents.service';
import { UpdateDocumentVisibilityDto } from './dto/update-visibility.dto';
import { JwtAuthGuard } from '../common/guards/jwt-auth.guard';
import { RolesGuard } from '../common/guards/roles.guard';
import { CurrentUser } from '../common/decorators/current-user.decorator';
import { buildContentDispositionHeader } from '../common/utils/sanitize-filename';
import { safeMimeType } from '../common/utils/safe-mime-type';
import { AuthUser } from '@lawfirm/shared';

@Controller('intake/:intakeId/documents')
@UseGuards(JwtAuthGuard, RolesGuard)
export class IntakeDocumentsController {
  constructor(private documentsService: DocumentsService) {}

  @Get()
  findByIntake(@Param('intakeId') intakeId: string) {
    return this.documentsService.findByIntake(intakeId);
  }

  @Post()
  @UseInterceptors(FileInterceptor('file'))
  upload(
    @CurrentUser() user: AuthUser,
    @Param('intakeId') intakeId: string,
    @UploadedFile() file: Express.Multer.File,
  ) {
    return this.documentsService.uploadForIntake(user, intakeId, file);
  }

  @Post(':documentId/versions')
  @UseInterceptors(FileInterceptor('file'))
  uploadVersion(
    @CurrentUser() user: AuthUser,
    @Param('intakeId') intakeId: string,
    @Param('documentId') documentId: string,
    @UploadedFile() file: Express.Multer.File,
  ) {
    return this.documentsService.uploadNewVersionForIntake(user, intakeId, documentId, file);
  }

  @Patch(':documentId/visibility')
  updateVisibility(
    @Param('intakeId') intakeId: string,
    @Param('documentId') documentId: string,
    @Body() dto: UpdateDocumentVisibilityDto,
  ) {
    return this.documentsService.updateVisibilityForIntake(intakeId, documentId, dto.visibleToClient);
  }

  @Get(':documentId/download')
  async download(
    @Param('intakeId') intakeId: string,
    @Param('documentId') documentId: string,
    @Query('version') version: string,
    @Res() res: Response,
  ) {
    const fileInfo = await this.documentsService.getFilePathForIntake(
      intakeId,
      documentId,
      version ? parseInt(version, 10) : undefined,
    );
    res.setHeader('X-Content-Type-Options', 'nosniff');
    res.setHeader('Content-Type', safeMimeType(fileInfo.mimeType));
    res.setHeader('Content-Disposition', buildContentDispositionHeader(fileInfo.filename));
    const stream = fs.createReadStream(fileInfo.path);
    stream.pipe(res);
  }
}
```

Note: unlike `DocumentsController`, no `@Roles(Role.ADMIN)` on the upload/version/visibility routes — `IntakeController`'s own routes (`intake.controller.ts`) have never restricted intake mutation to `Role.ADMIN`, so this stays consistent with that (any authenticated firm user who can edit an intake can attach a document to it).
