### A3. ปัญหาเรื่องคู่ความ (เรียงตามความรุนแรง)

1. **คู่กรณีกระจายอยู่ 3 ที่และหายตอนแปลงเป็นคดี**: `Intake.opposingParty`, `incidentDate` และ `estimatedDamage` ไม่ถูกคัดลอกไปที่คดี การตรวจผลประโยชน์ขัดกันจึงค้นไม่เจอคู่กรณีที่พิมพ์ไว้ใน `customFields.opposingParty`
2. **ตรวจผลประโยชน์ขัดกันไม่มีผลบังคับ**: คอมเมนต์ที่ `intake.service.ts:878` บอกว่ามีการบังคับ แต่จริง ๆ แล้ว decide/convert ไม่ได้เรียกตรวจ ส่วนการสร้างคดีตรงก็ไม่มีการตรวจเลย ช่อง `conflictOverrideReason` ก็ไม่มีหน้าจอไหนส่งค่าไป
3. **ใส่คู่ความตอนสร้างคดีไม่ได้** และบนมือถือดูหรือเพิ่มคู่ความไม่ได้เลย
4. **ทนายฝ่ายตรงข้ามเป็นแค่ข้อความ**: ใช้ซ้ำข้ามคดีไม่ได้ และค้นหาว่า "ทนายคนนี้เคยอยู่ฝั่งตรงข้ามกับเราคดีไหนบ้าง" ไม่ได้
5. แยก "คนจ้าง" กับ "คนจ่าย" ไม่ได้ และ partyRole ไม่มีผู้ร้อง/ผู้คัดค้าน
6. มือถือสร้างลูกความเป็นข้อความเปล่า จึงไม่มี Client ให้ออกบิลหรือเชิญเข้า portal
7. ลูกความคนที่ 2 เป็นต้นไปแก้ไขไม่ได้, `Case.subType` ไม่มีที่ใช้, ศาลเป็นข้อความเปล่าไม่ผูกทะเบียนศาล

### A4. ข้อเสนอ: แบบข้อมูลคู่ความแบบใหม่ (ทำเท่าที่จำเป็น)

ให้ **`CaseParticipant` เป็นแหล่งเดียวของ "ใครอยู่ในคดี"** (แบบเดียวกับ related contacts ของ Clio) โดยเพิ่ม:
- `clientId?` / `contactId?`: ผูกกับ Client ที่มีอยู่ ทำให้ลูกความ ผู้ว่าจ้าง และคู่ความค้นหาได้ในที่เดียว
- `representedById?`: ทนายฝ่ายตรงข้ามผูกกับคู่ความที่เขาว่าความให้
- `isBillTo` / `sharePercent`: แยกผู้จ่ายเงินออกจากผู้ว่าจ้าง (ย้ายมาจาก CaseCustomer ทีหลังได้ ไม่ต้องทำรอบแรก)

แล้วทำ 4 อย่างนี้:
1. ฟอร์มสร้างคดีมีส่วน **"คู่ความ"** ให้กรอกหลายแถว (บทบาท + ฝั่ง + ชื่อ) แทนช่องข้อความ "คู่กรณี" และใส่ฝั่งที่เราว่าความ (โจทก์/จำเลย/ผู้ร้อง/ผู้คัดค้าน)
2. ตอนแปลง intake เป็นคดี ให้แปลง `opposingParty` เป็น CaseParticipant ฝั่ง OPPONENT
3. ตอนบันทึกคดี ให้**ตรวจผลประโยชน์ขัดกันกับทุกชื่อในส่วนคู่ความโดยอัตโนมัติ** ถ้าเจอชื่อซ้ำให้กรอกเหตุผลก่อนบันทึก (ใช้ `conflictOverrideReason` ที่มีอยู่แล้ว) และให้ฝั่ง server บังคับด้วย
4. มือถือ: เพิ่มส่วนคู่ความในหน้าคดีและหน้าสร้างคดี และเลือกลูกความจาก Client จริง

## ส่วน B: Flow ตั้งแต่รับเรื่องจนปิดคดี

### B1. Flow ปัจจุบัน

```
[รับเรื่อง Intake]
 NEW_INQUIRY → CONTACTED → SCREENING → CONFLICT_CHECK → CONSULT_SCHEDULED
   → CONSULTED → WAITING_DOCUMENTS → PRE_LITIGATION_NOTICE → PROPOSAL → CLOSED
   (ข้ามขั้นหรือย้อนกลับได้ทุกขั้น: PATCH /intake/:id/stage)
   ├ assess              → SCREENING
   ├ ขอเอกสารจากลูกค้า   → WAITING_DOCUMENTS (เลื่อนให้อัตโนมัติ)
   ├ ร่างหนังสือบอกกล่าว  → PRE_LITIGATION_NOTICE
   ├ ลูกค้าไม่ตอบ        → NO_RESPONSE
   └ decide:
       ฟ้อง / เจรจาก่อน / ส่งหนังสือบอกกล่าว / ร้องหน่วยงาน → เปิดคดี (convert)
       ปรึกษาอย่างเดียว → CONSULTED
       อื่น ๆ           → REJECTED

[เปิดคดี] สร้างเลข ownRef = {prefix}{ปี พ.ศ.}{NNNN}
 คัดลอก: ลูกความ, ผู้ว่าจ้าง, ฝั่ง, ประเภทคดี, อายุความ (+ นัด DEADLINE), ทุนทรัพย์,
         การวิเคราะห์ฎีกา, ไฟล์, งานจาก intake, playbook, ประกัน, ทีม
         + งานแรก "เริ่มดำเนินการคดี" ให้ทนายเจ้าของคดี
 ❌ ไม่คัดลอก: คู่กรณี, วันเกิดเหตุ, ความเสียหาย

[ขั้นตอนคดี] PRE_LITIGATION → FILING → ANSWER → MEDIATION → HEARING
   → AWAITING_JUDGMENT → ENFORCEMENT → CLOSING → APPEAL → SUPREME
   กดปุ่มขั้นตอน → ระบบเสนองานของขั้นนั้นจาก playbook
     ├ "ย้ายอย่างเดียว"
     └ "ย้าย + สร้างงาน" (งานแม่ stage:X + งานย่อย, งานตาม SOP ต้องมีคนตรวจ)
   ถ้ายังไม่ได้จัดการงานที่เสนอ ระบบจะเตือนอีกครั้งตอนเปิดคดี

[ปิดคดี] GET outstanding (งานค้าง, นัดในอนาคต, เอกสารที่ยังไม่อนุมัติ)
 → POST close (สรุปปิดคดีอย่างน้อย 10 ตัวอักษร, ผลคดีไม่บังคับ, ถ้ามีงานค้างต้องยืนยันรับทราบ)
 → CLOSED → archive → ARCHIVED   (reopen → IN_PROGRESS)
 → ร่างอีเมลปิดคดี → อนุมัติ  (❌ อนุมัติแล้วไม่ได้ส่งจริง)
```

### B2. เทียบกับ Clio / Casefox

| เรื่อง | LexFlow | Clio | Casefox |
|---|---|---|---|
| ขั้นตอนคดี | enum ตายตัว 10 ขั้น | แต่ละสาขากฎหมายตั้งเองได้ + kanban | Case Stages ตั้งเองได้ |
| เปลี่ยนขั้นตอนแล้วทำอะไรต่อ | เสนองานจาก playbook ให้กดยืนยัน | Automated Workflow: ใส่ชุดงาน หรือสร้างเอกสารอัตโนมัติ | ใส่ Task Group เอง |
| สถานะ | 7 ค่า ตั้งเป็นค่าใดก็ได้อิสระ | Open / Pending / Closed | Active / Archived |
| ปิดคดี | ตรวจงานค้าง + สรุป | ปิดได้เลย | archive |

### B3. ปัญหาของ flow

1. เปลี่ยนขั้นตอนได้ทุกทิศทาง ทุกคนที่เข้าคดีได้ทำได้ และ**ไม่มีบันทึกใน CaseStatusLog** นอกจากนี้ขั้น APPEAL/SUPREME ไม่ sync กับชั้นศาล
2. **`PATCH status=CLOSED` ข้ามการตรวจของการปิดคดีได้** (สรุปปิดคดีและงานค้าง) และบนมือถือก็เลือกสถานะได้อิสระ
3. reopen แล้วขั้นตอนยังค้างอยู่ที่ CLOSING, ผลคดีไม่บังคับกรอก, ไม่มี checklist ปิดคดี (บิลสุดท้าย, คืนเอกสาร, แจ้งลูกความ)
4. อีเมลปิดคดีอนุมัติแล้วไม่ได้ส่งจริง
5. สร้างเลข ownRef ซ้ำซ้อน 2 ที่ และฝั่ง intake ไม่มี retry ถ้ากดพร้อมกันจะเกิด error 500
6. ขั้น INTAKE_REVIEW และ FACT_GATHERING ไม่มีทางไปถึง (dead)

### B4. ข้อเสนอ

1. บังคับให้การปิดคดีทำผ่าน `POST close` เท่านั้น (เอา CLOSED/ARCHIVED ออกจาก PATCH) และบังคับกรอกผลคดี
2. เปลี่ยนขั้นตอนคดีแล้วบันทึก log พร้อมระบุว่าใครเปลี่ยน ย้อนกลับได้แต่ต้องใส่เหตุผล และตอน reopen ให้กลับไปขั้นก่อนปิด
3. ใช้ ownRef generator ตัวเดียวทั้งระบบ
4. ระยะถัดไป: ให้สำนักงานตั้งขั้นตอนคดีเองได้ + automation (ดู gap report ระยะที่ 3)

### C3. Flow ส่งงานให้ตรวจ (ปัจจุบัน)

```
ผู้ทำ (assignee) ── "ส่งตรวจ" PATCH /tasks/:id/handoff (ใส่ note ได้เฉพาะบนเว็บ)
   │  ถ้ามี SOP: ระบบตรวจ checklist, ไฟล์แนบ และงานที่ขวางอยู่ก่อนส่ง
   ▼
PENDING_REVIEW: assignee ถูกเปลี่ยนเป็นผู้ตรวจ (หรือทนายเจ้าของคดี)
   │  ❌ ผู้ตรวจไม่ได้รับแจ้งเตือน (ต้องไปเห็นเองใน My Day หรือ operations)
   ├─ "อนุมัติ" POST accept → DONE
   │     แจ้งเฉพาะผู้ติดตาม ❌ คนทำไม่รู้ว่างานผ่านแล้ว
   │     → ถ้าเป็นงานทำซ้ำ สร้างรอบใหม่ / แจ้งงานที่รออยู่ว่า "เริ่มได้แล้ว" / workflow เดินต่อ
   └─ "ส่งกลับแก้" POST reject (บังคับใส่เหตุผล) → NEEDS_REVISION
         คืนงานให้คนที่ส่งตรวจล่าสุด + รีเซ็ต checklist ✅ แจ้ง LINE/push/inbox
```

**ส่งเอกสารให้ตรวจ (review rounds)** เป็นอีก flow หนึ่งที่แยกออกไป
- เลือกผู้ตรวจได้หลายคน + เกณฑ์ ALL หรือ ANY_ONE + กำหนดส่ง → เวอร์ชันเอกสารเปลี่ยนเป็น WAITING_REVIEW
- ผู้ตรวจอนุมัติหรือส่งกลับ (ต้องใส่เหตุผล) → APPROVED หรือ RETURNED_FOR_CHANGES
- ❌ **ไม่มีการแจ้งเตือนเลย** ไม่เตือนเมื่อใกล้ครบกำหนด ไม่มีบนมือถือ และไม่ผูกกับงาน

**Workflow** (แม่แบบหลายขั้น)
- แต่ละขั้นกำหนด role และจำนวนวัน → เลือกผู้รับงานเองหรือให้ระบบเลือกคนที่ว่างที่สุด → ต่อกันเป็นสายด้วย blockedBy
- ส่งกลับไปขั้นก่อนหน้าได้ และ freelance ภายนอกส่งงานผ่าน `/work` ได้

### C4. ปัญหาของงานและการส่งตรวจ

| # | ปัญหา | ผลกระทบ |
|---|---|---|
| 1 | **ส่งตรวจ, อนุมัติ, โอนงาน, พักงาน ไม่มีการแจ้งเตือน** | ผู้ตรวจไม่รู้ว่ามีงานรอตรวจ และคนทำไม่รู้ว่างานผ่านแล้ว นี่คือปัญหาที่ใหญ่ที่สุด |
| 2 | ส่งตรวจแล้ว assignee ถูกเปลี่ยนเป็นผู้ตรวจ | คนทำหายไปจาก "งานของฉัน" รายงานว่าใครทำอะไรจึงเพี้ยน |
| 3 | ผู้ตรวจต้องเป็น OWNER หรือ SENIOR เท่านั้น และมีได้คนเดียว | ทนายตรวจงานกันเอง (peer review) ไม่ได้ และตรวจหลายคนไม่ได้ (แต่เอกสารทำได้) |
| 4 | LAWYER มอบงานให้ผู้ช่วยไม่ได้ (คนที่มอบงานให้คนอื่นได้มีแค่ OWNER และ SENIOR) | ทนายต้องขอให้หัวหน้ามอบงานให้ |
| 5 | ส่งตรวจบนมือถือ/LINE ใส่ note ไม่ได้ และไม่มี checklist ตอนส่ง (ยกเว้นงานที่มี SOP) | ผู้ตรวจไม่รู้ว่าต้องดูอะไร |
| 6 | ไม่มีหน้าจอสำหรับเริ่มพักงาน และไม่มีสถานะ ON_HOLD | บนบอร์ด งานที่พักอยู่ดูเหมือนงานปกติ |
| 7 | อัปเดตรายวันไม่แจ้งใคร และคอมเมนต์ในงาน @mention ไม่ได้ | |
| 8 | ฟอร์มบนเว็บไม่มีรายละเอียด/งานที่ขวางอยู่/การทำซ้ำ ฟอร์มบนมือถือไม่มีความสำคัญ/ผู้ติดตาม | ฟอร์มสองฝั่งไม่ตรงกัน |
| 9 | เอกสารที่ส่งตรวจไม่มีการแจ้งเตือนเลย และฟิลด์ editorIds ไม่ได้ใช้ | |
| 10 | SOP มี 2 แบบ (หน้า SOP กับ routine ใน playbook) ที่ไม่เชื่อมกัน | สับสน |

### C5. ข้อเสนอ (เรียงตามคุ้มค่า)

1. **แจ้งเตือนทุกจังหวะของการส่งตรวจ** ผ่าน `AssignmentNotifierService` ที่มีอยู่แล้ว (inbox + push + LINE):
   - ส่งตรวจ → แจ้งผู้ตรวจพร้อม note และปุ่ม LINE quick action "อนุมัติ / ส่งกลับ"
   - อนุมัติ → แจ้งคนทำ
   - โอนงาน → แจ้งคนใหม่และคนเดิม
   - พักงาน, อัปเดตรายวัน (ถ้ามี blocker) → แจ้งทนายเจ้าของคดี
   - รอบตรวจเอกสาร: เปิดรอบ → แจ้งผู้ตรวจทุกคน, ใกล้ครบกำหนด → เตือน, ตัดสินแล้ว → แจ้งคนส่ง
2. **เก็บคนทำไว้**: เพิ่มฟิลด์ `submittedById` (หรือใช้ log HANDED_OFF ล่าสุด) แล้วแสดงงานในหน้า "งานของฉัน" ใต้หัวข้อ "รอตรวจ" แทนการเปลี่ยน assignee
3. **ส่งตรวจต้องมีสรุป**: บังคับกรอก note สั้น ๆ ("ทำอะไรไป / อยากให้ดูตรงไหน") ทั้งบนเว็บ มือถือ และ LINE
4. **ผ่อนกฎ**: ผู้ตรวจเป็นใครก็ได้ที่ role ≥ คนทำ และ LAWYER มอบงานให้ ASSISTANT หรือ OFFICE_MANAGER ได้
5. ฟอร์มสร้างงานบนเว็บและมือถือมีฟิลด์ชุดเดียวกัน + มีปุ่ม "พักงาน" + @mention ในคอมเมนต์
6. เชื่อมหน้า SOP กับ routine ใน playbook ให้เป็นสิ่งเดียวกัน (ทีหลัง)
