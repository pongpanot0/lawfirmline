# Research: user-defined Custom Fields สำหรับสำนวน/Case

วันที่สำรวจ: 2026-11-14 · ภาษา: ไทย · Source revision: `36d839e83f819bcd3fac29f84ad8f045edf0f116`

ขอบเขต: วิจัยผลิตภัณฑ์และสถาปัตยกรรม อ่าน source เพื่ออธิบายระบบปัจจุบันเท่านั้น ไม่แก้ application code ไม่ commit

## TL;DR และ MVP

ข้อเสนอด้านล่างเป็น **design recommendation** จากหลักฐาน ไม่ใช่ความสามารถที่มีอยู่แล้ว:

- ให้ firm จัดการ **field library** ของตัวเอง แยก definition ออกจากการนำไปใช้กับ CaseType และตำแหน่งบนหน้า; เลือก “ทุกประเภทคดี” หรือ “เฉพาะประเภท” ได้ ข้อมูล contact ต้องเป็นอีก entity scope ในอนาคต ไม่เก็บซ้ำในทุก Case (เทียบ Clio/Jira/TaxDome ในตาราง).
- ใช้ **relational definitions + `Case.customFields` JSONB** ต่อจากของเดิม; metadata มี tenant, immutable ID, type, label, options, version และ archive status. ยังไม่ย้าย values ทั้งระบบเป็น EAV และไม่สร้างคอลัมน์/DDL ใหม่เมื่อ admin เพิ่ม field.
- ทำ **server validation + partial field PATCH + optimistic concurrency + field change audit** ก่อนเปิด builder; ทุก writer รวม Web, Intake, REST/import และ system keys ต้องผ่านกติกาเดียวกัน ป้องกันข้อมูลหายจาก object replacement.
- MVP มี 6 types: short text, long text, number, date, single-select, boolean; field/option ID ไม่เปลี่ยนตาม label. Archive เก็บค่าเดิม; type ที่มีข้อมูลแล้วเปลี่ยนผ่าน field ใหม่และ migration preview.
- UX ให้ admin preview ก่อน publish; หน้า Case แสดงตาม groups/order พร้อม inline edit; Mobile อ่าน/แก้ types เดียวกันได้ แต่ builder อยู่ Web. Required เริ่มเป็น **ต้องครบก่อน advance workflow** ตามแนวระบบเดิม ไม่ขัดขวางการเปิด draft Case.
- สิทธิ์ต้องทำที่ backend ครอบคลุม list/detail/search/count/export/template/Mobile/API/MCP/AI context; `PII` flag ต้องมาพร้อม policy ไม่ใช่แค่ badge. Default ไม่ส่ง sensitive fields ให้ AI/portal โดยอัตโนมัติ.
- เริ่ม filter แบบ typed equality/empty และ number/date range พร้อม CSV + document merge สำหรับ fields ที่ผู้ใช้มีสิทธิ์; sort/aggregate arbitrary ทุก field และ automation ซับซ้อนเป็น later. ถ้า owner ต้องการ arbitrary reporting ตั้งแต่วันแรก ต้องทบทวน typed EAV/projection ก่อนล็อก MVP.

### สิ่งที่ ship แรก และสิ่งที่รอ

| MVP ที่นับว่าครบใช้งาน | Later เมื่อมี demand/หลักฐาน workload |
|---|---|
| Web admin library + applicability ทุก/บาง CaseType, section name/order, help text, preview/publish, rename/archive, option lifecycle | Reusable named field sets หลายชุด, per-case add/remove sets, industry starter packs, translations |
| 6 types, input validation ทุกช่องทาง, optional/required-before-advance, missing-info feedback ที่รองรับ `0/false` | Required-on-create/ตาม stage อย่างละเอียด, conditional visibility/dependent lists, formula/rollup/relation, multi-select, money/currency |
| Web+Mobile read/edit, partial patch มี version conflict, actor/source old/new audit, basic role-based view/edit allowlists ภายใน case access | Per-user/team ACL, approval workflows, advanced bulk edit และ Mobile admin builder |
| Selected custom columns, typed filters, permission-aware CSV export/import preview และ template merge variables; REST definitions/value contract | Global full-text ทุก field, arbitrary custom-field sort/pivot/aggregates, analytics materialization, import ที่สร้าง definitions อัตโนมัติ |
| API metadata redaction; MCP/AI ปิด custom-sensitive exposure โดย default จนบังคับ policy ครบ | MCP field discovery/filter/write หลังใช้ shared authorization+validation; public ecosystem/webhooks |
| Legacy adapter, reserved keys, dry-run backfill/reconcile/rollback | Typed search projection หรือ EAV เมื่อ benchmark แสดงความจำเป็น |

จำนวน 6 types และการแบ่ง phase เป็นข้อเสนอ ไม่ใช่ vendor parity หรือ effort estimate. MVP นี้เป็น product slice ที่มีหลาย surfaces; ไม่ควรใช้คำว่า “เพิ่ม JSON editor” ประเมินงานทั้งหมด.

## What we have today

### ขอบเขตหลักฐาน

เป็น static source inspection ของ revision ข้างต้น ไม่ใช่การยืนยัน production schema/data หรือการทดสอบ browser/device จริง ลิงก์ code ด้านล่างใช้ path จาก repository root พร้อม `file:line`; รายการที่บอกว่า “ไม่พบ” จำกัดอยู่ที่ consumers และเส้นทางที่สำรวจ ไม่ได้พิสูจน์ว่าไม่มี manual SQL/admin operation ภายนอก repo

### Validation, write semantics และที่แสดงค่า

- API create/update ตรวจ `customFields` แค่ว่าเป็น optional object (`@IsObject`), ไม่พบการตรวจ key/type/option/required ตาม `CaseType.fieldSchema` ก่อนบันทึก — `apps/api/src/cases/dto/case.dto.ts:163–165`, `:281–283`; service ส่ง object เข้า Prisma ตรง — `apps/api/src/cases/cases.service.ts:744–766`, `:894–914`.
- `required` ใช้ `missingCaseInfo`: ค่าทั่วไปต้องเป็น **string ที่ trim แล้วไม่ว่าง**; numeric `0` หรือ boolean `false` จะถูกนับว่าขาดถ้าเป็น required ในรูปแบบนี้ — `apps/api/src/cases/case-info.ts:23–31`. Journey/progress เรียก helper นี้ — `apps/api/src/cases/cases.service.ts:301–314`, `:401–436`. นี่คือ completeness ของ workflow ไม่ใช่ hard validation ของทุก save.
- Web new case อ่าน schema ของ type, ตัด 4 keys ที่มี input เฉพาะออก และ render select หรือ HTML input; event value เก็บเป็น string แม้ type number/date — `apps/web/src/app/(dashboard)/cases/new/page.tsx:133–138`, `:612–623`, `:300–303`. เมื่อเปลี่ยน type บนหน้าสร้าง จะล้างค่าเฉพาะที่กรอกไว้ ยกเว้น `incidentDate/estimatedDamage` และล้าง `chargeSection` — `:476–481` (เป็น unsaved draft ไม่ใช่ลบ DB case).
- Web overview edit ใช้ schema จาก type catalog (fallback detail ถ้ามี); render `text/number/date/select`, มีดาว required แต่ input custom ไม่ใส่ HTML `required` — `apps/web/src/components/cases/CaseOverviewForm.tsx:50–74`, `:145–150`. ตอน save trim เป็น string แล้ว client merge object เก่าก่อนส่ง — `apps/web/src/app/(dashboard)/cases/[id]/page.tsx:668`, `:750–755`.
- Case read view วน object โดยตรง ซ่อน `__costEstimate`, `chargeSection`, `opposingParty`, แปลง label เฉพาะ incident date/damage; key อื่นแสดง raw key ไม่ใช้ label จาก definition — `apps/web/src/app/(dashboard)/cases/[id]/page.tsx:1292–1295`. ดังนั้น rename label/ชนิดใหม่จะไม่สะท้อนครบทุกจุดโดยอัตโนมัติ.
- API PATCH ปัจจุบัน **แทนที่ JSON object ทั้งก้อน** ไม่ใช่ server merge ต่อ key — `apps/api/src/cases/cases.service.ts:903–914`. การ merge ฝั่ง Web ไม่ป้องกัน stale concurrent writers; risk = lost update ของ key อื่น เป็น inference จาก write semantics ไม่ใช่ incident ที่ reproduce แล้ว.
- Intake → Case ส่ง `incidentDate` แบบ `YYYY-MM-DD` และ `estimatedDamage` แบบ number เข้า JSON — `apps/api/src/intake/intake.service.ts:1289–1297`. Web กลับใช้ string; ต้องรองรับ legacy mixed representation ก่อนบังคับ strict typing.
- JSON เดียวมี reserved/internal data: `CASE_COSTS_KEY='__costEstimate'` (`apps/web/src/lib/case-costs.ts:1`); cost editor เก็บ `JSON.stringify(lines)` และ read-merge-write ทั้ง object — `apps/web/src/components/cases/CaseCostCalculator.tsx:173–191`. ห้ามสร้าง user field มาชนหรือ normalize ทุก key โดยไม่รู้ consumer.
- Mobile: `CaseDetail` ไม่มี `customFields`/`fieldSchema`; create/edit body ไม่มี custom values — `apps/mobile/src/api/types.ts:89–102`, `apps/mobile/app/case/new.tsx:100–109`; ค้นสอง identifiers ทั่ว `apps/mobile` ไม่พบ generic renderer. API อาจส่ง JSON มาได้ แต่ไม่มีหลักฐานว่า Mobile แสดง/แก้ได้. การแก้ core field ที่ไม่ส่ง JSON จะไม่แทนที่ JSON เพราะ service ใช้ undefined เมื่อไม่ได้ส่ง.

| ความสามารถ | ข้อสรุปจาก code |

| Reports | report volume group by `caseTypeId` และ fixed metrics; ไม่พบ custom-field report dimension/filter — `apps/api/src/reports/reports.service.ts:189–208` |

| Permissions | `CaseAccessService` scope firm + case access, ปฏิเสธ EXTERNAL — `apps/api/src/common/services/case-access.service.ts:24–60`; PATCH มี CaseAccessGuard (`apps/api/src/cases/cases.controller.ts:81–88`). ไม่พบ view/edit ACL ต่อ custom key; definition admin capability ก็ยังจัดการ schema ไม่ได้ตาม DTO ข้างต้น |
| Audit history | update log เฉพาะ status/stage/owner; owner audit มี from/to — `apps/api/src/cases/cases.service.ts:952–988`. ไม่พบ field-by-field old/new history หรือ definition history ในเส้นทาง customFields; ไม่ควรนับ `updatedAt` เป็น audit |
| AI / MCP | พบ AI case summary select JSON ทั้งก้อน แล้ว serialize เป็น context — `apps/api/src/intake/intake-precedent-analysis.service.ts:514–540`. MCP read tools ลงทะเบียนผ่าน secretary definitions/readSchemas — `apps/api/src/mcp/mcp-tools.service.ts:63–73`; ไม่พบ dedicated custom-field schema/value/filter tool. ต้อง review field policy ครอบคลุม AI context ด้วย ไม่ใช่แค่ REST/UI |

**Gap หลัก:** มี storage และ renderer ขั้นต้นแล้ว แต่ขาด firm-managed definitions, shared validation, stable identity/lifecycle, granular patch+audit, output integration และ data-access projection. การเปิด textarea ให้แก้ `fieldSchema` อย่างเดียวจึงยังไม่ครบ feature.

## UX recommendations

### Admin builder

เส้นทางแนะนำ: Settings → ข้อมูลเฉพาะ → สำนวน/Case → Field library. ใช้ capability เดิม `manageFirmContent` สำหรับเข้าจัดการ แล้วให้ owner เป็นผู้กำหนดว่า office manager จัดการ sensitivity/ACL ได้หรือไม่ (ปัจจุบัน capability นี้รวม OWNER และ OFFICE_MANAGER — `packages/shared/src/firm-capabilities.ts:26–37`).

1. หน้า list แสดง label, type, ใช้กับ type ใด, section, required policy, privacy, usage count, active/archived; มีค้นหาเพื่อลด field ซ้ำ.
2. “เพิ่มช่องข้อมูล” เลือก type → label/help → ใช้ทุกประเภทหรือเลือกประเภท → section/order → optional หรือ required ก่อน advance → view/edit roles → preview. สร้าง machine ID อัตโนมัติ ไม่ให้แก้ key เป็นส่วนหนึ่งของ rename.
3. Picklist จัดการ option ID/label/order แยกกัน; เพิ่ม/rename/reorder ไม่ rewrite values. Archive option = เลือกใหม่ไม่ได้ แต่ record เก่ายังแสดง/filter/export ได้; merge options ต้องมี impact preview และ audit เป็นงานแยกภายหลัง.
4. ก่อน publish แสดงจำนวน Case/definitions/templates/filters ที่ได้รับผล; type change, new required, archive และเอา field ออกจาก type ต้องอธิบายผลต่อข้อมูลเก่า. Draft preview ไม่เปลี่ยน production definition จน publish.
5. Reorder ใช้ drag พร้อมปุ่ม “ขึ้น/ลง” สำหรับ keyboard; label/help/error มี accessible association, error summary พา focus ถูกช่อง; Thai labels ต้อง wrap ได้ ไม่ใช้ placeholder แทน label.

Conditional visibility เป็น later: เริ่มจาก equality ของ single-select/boolean ภายใน Case เดียว ไม่เปิด arbitrary expressions; ตรวจ dependency cycles ตอน publish, preserve hidden values และ required มีผลเฉพาะเมื่อ visible/applicable. ถ้าผู้ใช้ไม่มีสิทธิ์อ่าน field ที่เป็นเงื่อนไข ต้องไม่เผยค่าผ่านการปรากฏของช่องอื่น. นี่เป็นข้อเสนอสำหรับ phase ถัดไป อิงแนว conditional-required ของ Filevine และ dependent options ของ Actionstep ไม่ใช่ฟีเจอร์ที่มีแล้วใน repo.

Patterns ที่รองรับข้อเสนอ: Clio แยก field/set และ admin rights; Jira แยก definition/context; HubSpot แยก internal option value จาก label และ archive option ไม่ล้าง record เดิม; Notion API รักษา property ID หลัง rename. เป็นการสังเคราะห์ ไม่ใช่อ้างว่า vendor ใดมี UX เหมือนข้อเสนอทุกขั้น ([Clio](https://help.clio.com/hc/en-us/articles/9285493193115-Get-Started-With-Custom-Fields), [Jira contexts](https://support.atlassian.com/jira-cloud-administration/docs/what-are-field-contexts/), [HubSpot options](https://knowledge.hubspot.com/properties/manage-enumeration-property-options), [Notion property IDs](https://developers.notion.com/reference/page-property-values)).

Clio Sets กับ Fields docs อธิบายลำดับภายในชุดต่างกันตาม experience/version; จึงยืนยันเฉพาะการจัดชุดและสั่งลำดับทั่วไป ไม่ใช้เป็นหลักฐานว่า selection order จะเหมือนกันทุก rollout ([Clio Field Sets](https://help.clio.com/hc/en-150/articles/9285516718491-Clio-Manage-Custom-Field-Sets), [Clio Fields](https://help.clio.com/hc/en-us/articles/9285496802331-Clio-Manage-Custom-Fields)).

### หน้า Case และการเปลี่ยนประเภท

- สรุป core fields เดิมไว้ก่อน ตามด้วย “ข้อมูลเฉพาะ” ที่ใช้ definition labels/type formatting; จัด sections ตามงาน ไม่เรียง raw JSON keys; empty ใช้ “ยังไม่ระบุ”, false ใช้ “ไม่ใช่”, 0 แสดง 0.
- แก้ทีละช่องหรือทั้ง section พร้อม Save/Cancel; PATCH เฉพาะ field ที่เปลี่ยน. ถ้า version เก่า ให้แสดงค่าล่าสุดและ draft ของผู้ใช้ ไม่ auto-overwrite. ขณะ error เก็บ draft และแสดง field-specific error.
- Create draft เก็บ core minimum เดิม; required-before-advance แสดง checklist/link ไปแก้เมื่อจะเลื่อน workflow. Strict type/option validation ยังใช้ทุก save ที่ส่งค่ามา ไม่ให้ draft เป็นทางเลี่ยง validation.
- เปลี่ยน CaseType ต้อง preview ว่าอะไรเพิ่ม/ไม่ใช้แล้ว; ค่าของ fields ที่ไม่ applicable เก็บไว้ใน “ข้อมูลเดิมจากประเภทก่อนหน้า” แบบอ่านได้ตามสิทธิ์ ไม่ล้างอัตโนมัติ. Required rule ใหม่เริ่มเมื่อผู้ใช้ทำ action ที่อยู่ในขอบเขต rule ไม่ retroactively ทำให้ unrelated edit ล้มเหลว.
- Field history ดู actor/time/source/old→new; การ rename แสดง label ปัจจุบันในหน้าทั่วไป แต่ audit เก็บ label+definition version ณ เวลานั้นเพื่ออ่านเหตุการณ์เก่าได้.
- Bulk edit เป็น later: เลือก Case ในสิทธิ์ → เลือก field ที่ applicable → แสดง eligible/skipped/conflict counts → preview → background job ที่ resumable และมี per-case audit; ไม่ใช้ one-click replace JSON ทั้งก้อน.

การ retire ต้องไม่ใช้ hard delete เป็น default. ไม่ควรคัดลอก retention ของ vendor มาโดยไม่คิด: HubSpot archived property ถูกลบถาวรหลัง 90 วัน ขณะที่ Karbon delete definition ลบ values ถาวร; ของเราเสนอ archive ไม่มีกำหนด purge อัตโนมัติจนกำหนด retention policy ([HubSpot lifecycle](https://knowledge.hubspot.com/properties/organize-and-export-properties), [Karbon lifecycle](https://developers.karbonhq.com/guides/custom-fields/)).

### Mobile

ใช้ definitions/value contract เดียวกับ Web: section collapse, required-first shortcut, native date/number/select controls, multiline editor, แสดง denied/archived ตาม backend. อ่าน/แก้ MVP ทั้ง 6 types ไม่ให้มี fields ที่ Web บังคับแต่ Mobile กรอกไม่ได้. ไม่ทำ builder บน Mobile ช่วงแรก; ถ้ามี cached draft ให้ผูก definition revision และตรวจสิทธิ์/validation ซ้ำตอน reconnect.

Clio เป็นตัวอย่างที่ต้องตรวจ parity จริง: official Mobile docs จำกัด entry/edit custom fields ที่ marked default และ required และให้ใช้ Web สำหรับที่เหลือ จึงไม่ควรสมมติว่า competitor Mobile เท่า Web ทุกส่วน ([Clio Mobile](https://help.clio.com/hc/en-us/articles/9289682246427-Mobile-App-Matters-and-Matter-Notes)). Notion จัด property access rules บน desktop/Web แต่บังคับบน Mobile ได้ ([Notion property access](https://www.notion.com/help/database-property-access)).

### MVP field types และ canonical semantics

| Type | Value / validation ที่เสนอ | UX และข้อจำกัด |
|---|---|---|
| Short text | JSON string; trim boundary whitespace ตามนโยบาย; max length ระบุใน definition | ใช้เลขบัตร/เลขคดี/รหัส/โทรศัพท์ที่เป็น identifier เป็น text เพื่อเก็บ leading zeros; ไม่สร้าง field ซ้ำ core |
| Long text | JSON string; preserve newlines; จำกัด length/bytes ที่ server | Plain text ไม่รับ HTML หรือ executable formulas |
| Number | finite JSON number; optional min/max และ precision ที่นิยามชัด; ไม่รับ NaN/Infinity | ไม่ใช้กับเงินหรือเลขยาวเกิน safe precision; 0 เป็นค่าที่มีข้อมูล |
| Date | JSON string `YYYY-MM-DD` Gregorian validated calendar date | แสดง Thai locale/ปี พ.ศ. ได้ที่ UI แต่ไม่เก็บ พ.ศ. ปะปน ไม่ใช้ timezone timestamp กับ date-only |
| Single-select | immutable option ID จาก definition; ปฏิเสธ unknown/new archived option | เก่าอ่านได้แม้ option archived; rename label ไม่ rewrite ID |
| Boolean | JSON boolean `true/false`; missing คือยังไม่ตอบ | ตัวเลือก “ใช่/ไม่ใช่/ยังไม่ระบุ”; ไม่ใช้ unchecked ที่แยก false จาก missing ไม่ได้ |

ตัวเลข limit ของ field/option/text ยังไม่เสนอเป็น capacity guarantee: owner ต้องกำหนดหลังเห็น inventory/workload. Later money ใช้ Decimal + currency semantics แยก; multi-select/relation/file/formula มี validation/permission/report costs เพิ่ม จึงยังไม่อยู่ใน MVP. เปลี่ยน type ได้เฉพาะ field ที่ยังไม่มี values/dependencies; ที่มีแล้วสร้าง field ใหม่ → conversion preview → backfill พร้อม errors → archive เก่า ไม่ลบต้นฉบับ.

## Data model และ trade-offs

### เปรียบเทียบทางเลือก

ตารางนี้เป็น engineering assessment จากเอกสาร DB/ORM ไม่ใช่ benchmark ของ application:

| ทางเลือก | Filtering / sorting / reporting | Validation / audit / migrations | Tenant / performance / complexity |
|---|---|---|---|
| A. `Case.customFields` JSONB + schema JSON เดิม | GIN ช่วย predicates บางชนิด; range/order/group ตาม extracted type ต้องออกแบบเพิ่ม | Dynamic validation/audit ทำเอง; schema JSON เปลี่ยนง่ายแต่ identity/dependency/version ขาด | อ่าน case ง่าย ต่อของเดิมเร็ว; no FK ต่อ key/option, row lock ร่วมกัน; metadata governance ยังไม่พอ |
| B. Typed EAV: `Definition` + `Value` | B-tree `(firmId,fieldId,valueNumber/valueDate/valueText,caseId)` ช่วย type-specific queries; หลาย field ใช้ joins/EXISTS; report ตารางกว้างต้อง pivot | typed columns, FK, one-value-per-field และ check ว่ามี typed column เดียว; dynamic option/rules ยังต้อง validate; audit ผูก value ได้ | isolate value rows ได้ละเอียด; จำนวนแถว/ดัชนี/transaction/joins มากขึ้น; ไม่รับประกันว่าเร็ว/ช้ากว่า JSONB ทุกงาน |
| C. Hybrid metadata relational + JSONB values **แนะนำ MVP** | เริ่ม typed predicates ที่จำกัด workload; hot expressions/projection เพิ่มเมื่อวัดจริง | Definitions/assignments/options/version relational; shared validator + diff audit; legacy values อยู่เดิม | ไม่ต้อง rewrite ทุก Case; row-lock/lost-update ต้องแก้; arbitrary sort/report ยังมีต้นทุน |
| D. C + typed search projection (later) | indexed typed rows สำหรับ fields ที่ใช้ค้น/รายงานบ่อย; query builder แยกจาก canonical write | projection rebuild/reconcile/version; update ใน transaction เดียว หรือประกาศ lag | ขยาย query โดยไม่ย้าย authority ของค่า; ถ้าปล่อยสองฝั่งเขียนเองจะเกิด drift |

CYBERTEC แสดง EAV เพิ่ม writes/joins ในตัวอย่าง แต่บาง update/aggregate มีประโยชน์; ใช้เป็นตัวอย่าง trade-off ไม่ใช้ชื่อบทความสรุปว่า EAV แย่ทุกกรณี ([CYBERTEC EAV design](https://www.cybertec-postgresql.com/en/entity-attribute-value-eav-design-in-postgresql-dont-do-it/)). Crunchy Data อธิบายการเลือก JSONB indexes ตาม query shape ([Indexing JSONB in Postgres](https://www.crunchydata.com/blog/indexing-jsonb-in-postgres)).

### Model ที่เสนอ (conceptual ไม่ใช่ migration ที่พร้อม execute)

| ส่วน | หน้าที่ / invariants |
|---|---|
| `CustomFieldDefinition` | firmId, immutable id/storageKey, entityKind=`CASE`, label/help, type, status, revision, sensitivity, read/write policy; unique `(firmId,storageKey)`; key ของ field ใหม่ใช้ generated opaque ID ไม่ใช้ label |
| `CustomFieldOption` | firmId, definitionId, immutable optionId, label, position, archivedAt; composite ownership/FK ไป definition; ไม่ reuse option ID หลัง retire |
| `CustomFieldAssignment` | firmId, definitionId, scope=`ALL_CASE_TYPES` หรือ specific CaseType, section label/order, field order, required policy; required อยู่ที่ assignment เพราะประเภทหนึ่งอาจบังคับ อีกประเภทไม่บังคับ |
| `Case.customFields` | canonical values สำหรับ MVP; legacy keys คงอยู่ผ่าน mapping; keys ใหม่ใช้ storageKey/ID; ไม่ผูกข้อมูลกับ localized labels; reserved/system-owned keys เป็นคนละ write policy |
| Definition revision / value audit | ใช้ audit infrastructure เดิมเมื่อรองรับ payload/retention/ACL ได้ พร้อม definition snapshot/version; ถ้าเดิมไม่รองรับค่อยแยก model ไม่จำเป็นต้องสร้าง event-sourcing platform |
| Legacy compatibility | อ่าน `CaseType.fieldSchema` เป็น fallback ระหว่าง rollout; ภายหลังอาจ compile schema สำหรับ old readers เป็น derived output โดยไม่เปิดให้แก้เป็น authority อีกชุด |

ขอบเขต ALL vs specific ต้อง explicit และ unique จริง: อย่าใช้ nullable `caseTypeId` กับ composite unique แล้วคิดว่า PostgreSQL จะกัน duplicates ของ NULL เสมอ. Resolve applicability ด้วย deterministic union/dedup ตาม field ID; ถ้า all + specific ให้ specific override placement/required โดยไม่สร้างค่า field ซ้ำหนึ่ง Case. MVP section เป็น layout metadata ได้ ยังไม่ต้องมี reusable FieldSet engine.

Contact/Company/Job อนาคตมี definition scope แยก; ตั้งชื่อ UI ตาม profession ได้ แต่ไม่เปลี่ยน Case schema ทั้งระบบเป็น universal entity ตั้งแต่ตอนนี้. ข้อมูลที่มี behavior สำคัญแล้ว เช่น participants, claimedAmount, limitationDeadline ยังคงเป็น core columns/relations.

### JSONB indexes, Prisma และ query contracts

- GIN `jsonb_ops` รองรับ existence/containment/jsonpath operators; `jsonb_path_ops` ไม่รองรับ key-exists `?/?|/?&`. เลือกจาก predicates จริง ไม่เปิด path_ops แล้วสัญญาว่าค้น missing key ได้ทุกแบบ ([PostgreSQL JSON indexing](https://www.postgresql.org/docs/current/datatype-json.html#JSON-INDEXING)).
- GIN ไม่ให้ numeric/date range sort อัตโนมัติ; built-in B-tree ส่ง ordered results ได้. Extract/cast ให้ตรง type และ query expression; index มีต้นทุน writes. Date/timestamp cast ต้องตรวจ immutability/representation ก่อนใช้ expression index; invalid legacy data อาจทำให้ cast/build index fail ([ORDER BY](https://www.postgresql.org/docs/current/indexes-ordering.html), [expression indexes](https://www.postgresql.org/docs/current/indexes-expressional.html), [CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)).
- ไม่ทำ per-firm/per-field DDL ทุกครั้งที่ admin เพิ่ม field; เริ่ม tenant index + bounded typed filters วัดจริง แล้วเลือก shared GIN หรือ hot indexes/projection. Index ไม่ใช่ access policy; ทุก query ต้องรวม firmId + case access ก่อน field predicates.
- repo ประกาศ Prisma `^6.3.1` — `apps/api/package.json:27`, `:39`; ใช้ versioned v6 docs. JSON path filter ทำได้ แต่ v6 Client ไม่รองรับ JSON-property sorting/key-presence predicate; complex query ใช้ parameterized raw SQL หรือ typed projection ไม่ sort/filter ใน memory หลัง paginate. JSON insensitive mode ต้องตรวจ installed version (doc ระบุเริ่ม 6.4) ก่อนใช้ ([Prisma v6 JSON](https://www.prisma.io/docs/orm/v6/prisma-client/special-fields-and-types/working-with-json-fields)).
- Prisma รองรับ GIN operator class แต่ expression indexes ต้อง custom SQL migration; `CREATE INDEX CONCURRENTLY` ทำใน transaction block ไม่ได้ ต้องวาง rollout/cleanup invalid indexes แยก ([Prisma indexes](https://www.prisma.io/docs/orm/v6/prisma-schema/data-model/indexes), [unsupported features](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/unsupported-database-features), [PostgreSQL CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)).
- กำหนด filter API เป็น typed allowlist: text/select/boolean equality, empty/not-empty, number/date range, bounded AND conditions; server resolve field ID → trusted definition/path. ปฏิเสธ hidden field filters/counts และ operator ที่ไม่ตรง type; ไม่ให้ client ส่ง raw SQL/JSONPath. MVP sort core columns เท่านั้น; ต้องมี stable tie-breaker และ server pagination ก่อนโหลด 100k cases.
- JSONB update ยังล็อกทั้ง Case row; partial PATCH ต้องใช้ guarded `version`/OCC หรือ row lock + merge ใน transaction. Include value diff audit ใน transaction เดียว; version conflict return 409 พร้อม refresh/reapply flow ([JSON storage/update considerations](https://www.postgresql.org/docs/current/datatype-json.html), [Prisma OCC](https://www.prisma.io/docs/orm/v6/prisma-client/queries/transactions#optimistic-concurrency-control)).

ข้อเท็จจริงเรื่อง optimizer ไม่ควรอ้างจากบทความเก่าโดยไม่ระบุเวลา: Heap เคยรายงานปัญหา JSONB statistics แต่ PostgreSQL ปัจจุบันสร้าง extended statistics บน expressions ได้; ต้อง ANALYZE/ตรวจ query plan จริง ([Heap historical experience](https://www.heap.io/blog/when-to-avoid-jsonb-in-a-postgresql-schema), [CREATE STATISTICS](https://www.postgresql.org/docs/current/sql-createstatistics.html)).

### ประเมินขนาด ~100k cases/firm

ยัง **ไม่มี benchmark หรือ latency proof**. จำนวน Case อย่างเดียวตอบไม่ได้ว่า JSONB/EAV อะไรเร็วกว่า: ต้องรู้ populated fields/case, bytes/value, tenant skew, selectivity, report width, concurrency และ index budget.

ตัวอย่าง *estimate เชิงคณิตศาสตร์*: 100,000 cases × 20 populated fields = 2,000,000 EAV value rows ต่อ firm ไม่ใช่จำนวนข้อมูลจริง ไม่รวม indexes/history และไม่ใช่หลักฐานว่า DB รับไม่ไหว.

Benchmark gate ที่เสนอ: tenant ใหญ่/เล็กหลายราย, ค่าเบาบาง/ค่าซ้ำสูง, equality/empty/range, 2–5 field AND, ORDER BY+LIMIT, count/export, concurrent different-key/same-key writes; เก็บ `EXPLAIN (ANALYZE, BUFFERS)`, p95, DB CPU, index bytes, write cost และข้อมูลรั่วข้าม firm. 2–5 predicates เป็น workload proposal ไม่ใช่ product limit. ตั้ง SLO ร่วมกับ owner ก่อนลงมือ; ถ้าต้อง arbitrary sort/pivot ทุก field จากแรก ให้เลือก typed value authority/projection ตาม benchmark แทนรับปาก JSONB อย่างเดียว.

## Migration โดยไม่เสียข้อมูล

ขั้นตอนนี้เป็น **migration proposal** ยังไม่ได้ execute กับ DB ใด การแก้ application code ไม่อยู่ในงานวิจัยนี้.

1. **Inventory + backup ก่อนเปลี่ยน contract:** export schema JSON/values ต่อ firm/type, distribution ของ key/type/length, orphan keys, reserved keys, empty/null, numeric strings และ documents/templates ที่อ่านค่า. เก็บ snapshot raw JSON + case ID/version/checksum ใน backup ที่มี access/retention ชัด; ห้ามเดาจำนวน rows จาก defaults ปัจจุบัน.
2. **Classify core/system/user:** `chargeSection`, `incidentDate`, `estimatedDamage` มี dedicated consumers; `__costEstimate` เป็น system-owned serialized data ไม่ใช่ user text; `opposingParty` เคยย้ายไป participants และ `claimAmount` เคย backfill เข้า claimedAmount. ตรวจ migration history ก่อนเสนอให้ backfill ซ้ำ — `apps/api/prisma/migrations/20261011130400_parties_single_source/migration.sql:4–37`, `apps/api/prisma/migrations/20260912090000_backfill_claimed_amount_from_custom_field/migration.sql:1–11`. Keys ไม่รู้จักเก็บเป็น legacy/orphan จนมีคนจัดประเภท ไม่ drop.
3. **Expand metadata ก่อน:** สร้าง relational definitions/options/assignments จาก schema ที่มีจริงต่อ firm พร้อม mapping `(firmId,caseTypeId,legacyKey)` → field ID/storageKey. ชื่อ key เหมือนกันต่าง type/firm ห้าม auto-merge; ชื่อเหมือนแต่ความหมายต่างต้องแยก definition. Legacy storageKey เดิมคงอยู่ได้ และ key ใหม่ใช้ generated ID; ถ้าจำเป็น remap key ต้องเก็บ mapping/ต้นฉบับ. ไม่เปิดทุก field ให้ทุก CaseType อัตโนมัติ.
4. **Compatibility reader:** อ่าน definition ใหม่ถ้ามี mapping มิฉะนั้นอ่าน legacy schema; render ค่าที่เก่า/archived/ไม่อยู่ใน type ปัจจุบันแบบ labeled legacy. `CaseType.fieldSchema` ยังอ่านได้แต่หยุดใช้เป็น editable authority ใหม่; หากต้องส่งให้ old clients ให้ compile เป็น derived snapshot. ไม่ใช้ JSON key rename เป็นการย้าย metadata.
5. **Dry-run normalization:** เก็บรายงานทุกค่าที่แปลงไม่ได้และ raw original; canonical number/date/boolean/select ต้อง explicit. `estimatedDamage` number จาก Intake และ string จาก Web ต้อง preserve meaning; `0`, `false`, empty, JSON null, SQL NULL และ missing แยกกัน. ห้ามตีความวันที่กำกวมหรือพ.ศ./ค.ศ. เอง; field ที่ definition ยังไม่ชัดคง legacy pending.
6. **Canonical writer + rollout gate:** ทุก writer ใช้ shared validation/access/audit/partial patch; Web Overview, CaseSummaryPanel, CostCalculator, create form, Intake conversion, Mobile, REST/import และ AI summaries ต้องอยู่ใน rollout matrix. Existing full-object PATCH ยังเป็น replacement contract; อย่าเปลี่ยนเป็น merge อย่างเงียบ ๆ. Version endpoint/contract ใหม่หรือ compatibility adapter ที่รักษา unknown keys แล้ว deprecate เก่าพร้อมติดตาม traffic.
7. **Resumable batch backfill:** batch ต่อ tenant/cursor, optimistic case version, idempotent mapping และ validation errors ที่ retry ได้; audit migration actor/source. ไม่ hold transaction ครอบ 100k cases; ไม่เขียนทับ Case ที่มี concurrent update; projection ถ้ามีเป็น derived write ใน transaction หรือ rebuild ได้จาก canonical JSON.
8. **Reconcile ก่อน switch:** เทียบ case counts, per-key populated counts, raw-value checksums/mapping, invalid rows, before/after sample output ของ Web/Mobile/CSV/print/templates/journey. Verify orphan/internal keys ยังคงครบ และ cross-tenant tests ผ่าน. เงื่อนไขเสร็จต้องเป็น zero unexplained loss ไม่ใช่เพียง script exit 0.
9. **Switch/read compatibility แล้วค่อย contract:** rollout ทีละ firm; เปิด writer ใหม่หลัง reader รองรับ; monitor conflict/error/latency; retire schema JSON writer เมื่อไม่มี traffic เก่าแล้ว. ไม่ purge legacy data อัตโนมัติ. Rollback ต้องคืน feature flag/reader ได้โดยยังอ่านข้อมูลที่ writer ใหม่สร้างแล้วผ่าน mapping ไม่ใช่ restore backup ทับข้อมูลใหม่ทั้งหมด.

Rollback gate: ถ้า conversion fail ให้หยุดเฉพาะ batch/field และเก็บ raw values; ถ้า counts/checksums ต่างให้ยังไม่ contract; backup เป็น disaster recovery แยกจาก reversible rollout. ไม่มีขั้นใดลบ legacy `Case.customFields` ทั้ง object.

## Governance checklist

ทั้งหมดด้านล่างเป็น **acceptance checklist ที่เสนอ**; ไม่ใช่คำรับรองว่าระบบหรือ vendor ผ่านแล้ว.

### Access และ tenant isolation

- [ ] แยกสิทธิ์ manage definition / view value / edit value / export / use in template / AI-MCP exposure; case access ยังเป็นเงื่อนไขแรกเสมอ. Field ACL ห้ามทำให้คนได้เข้าคดีที่ปกติไม่มีสิทธิ์.
- [ ] Basic role allowlists บังคับ server-side ทุก list/detail/change/filter/count/group/CSV/template/Mobile/REST/MCP/AI serializer; role ที่แก้ definition ได้ไม่ควรขยาย field read/export policy เกินอำนาจตัวเองได้โดยเงียบ.
- [ ] Hidden values ไม่ปรากฏใน raw list JSON, search snippets, autocomplete, errors, exports, generated docs, audit viewer หรือ cached responses; ห้าม filter/count/group ด้วย fields ที่ไม่มีสิทธิ์เพื่อป้องกัน inference. Redaction เหมือนกันทุก surface.
- [ ] Metadata/options/assignments/audits มี firmId; composite constraints/FK ownership ตรวจ definition, case, option และ type ว่ามาจาก firm เดียวกัน. Unknown/cross-tenant field IDs ปฏิเสธโดยไม่เปิดเผยว่ามีอยู่ใน firm อื่น.
- [ ] RLS เป็น defense in depth ได้ แต่ Case-row RLS ไม่ใช่ JSON-key permission; table owner/superuser/BYPASSRLS มี bypass semantics ต้องออกแบบ role จริง. JSONB dynamic constraints ที่อ้างอีกตารางไม่รับประกันด้วย CHECK ธรรมดา; ต้อง service validation และ FK/trigger ตาม boundary ที่เลือก ([PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)).

“Hide column” ไม่ใช่ field security และ “read-only” ไม่ใช่ hide: Airtable ระบุ edit permissions ไม่ลด visibility ใน base; Filevine obsolete ยังเขียนผ่าน API ได้. ต้องนิยาม lifecycle กับ authorization แยกกัน ([Airtable](https://support.airtable.com/articles/2296468758-airtable-field-and-table-editing-permissions), [Filevine API](https://support.filevine.com/hc/en-us/articles/29259311975707-API-General-Q-A)).

### PII / PDPA และ audit

- [ ] Definition metadata มี data classification/purpose, sensitive flag, retention policy reference, export/AI/portal exposure policy; field label ไม่ใช่ตัวตัดสินว่าเป็น PII. ค่าเริ่มต้น sensitive ไม่ถูกส่งให้ external AI/portal จนอนุญาตชัดเจน.
- [ ] ผู้รับผิดชอบกำหนด lawful basis/notice/retention/legal hold ตามประเภทข้อมูลจริง; ไม่สรุปว่าทุกข้อมูลคดีใช้ consent เสมอ และไม่อ้างว่าเพิ่ม flag แล้ว PDPA compliant.
- [ ] Value audit บันทึก firm/case/field ID, definition revision, before/after, actor, channel (Web/Mobile/API/import/MCP/system), time, request/batch ID ใน transaction เดียวกับ write. เก็บ absence/clear/0/false แยกกัน; ไม่ใส่ sensitive old/new ลง general application logs.
- [ ] Definition audit แยก create/rename/options/order/applicability/required/type/archive/policy change; revision optimistic locking ป้องกัน admin สองคน publish ทับกัน; revalidate definition revision ตอน write values.
- [ ] Audit access/retention จำกัดตาม field data classification; บันทึกการ export/access ของ sensitive fields ตาม policy. การ archive ไม่อนุญาต hard-delete audit/values; purge/subject rights/legal hold ต้องมี workflow และ authority ต่างหาก.

ฐานกฎหมายที่ตรวจอ่านได้: ประกาศคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล **มาตรการรักษาความมั่นคงปลอดภัยของผู้ควบคุมข้อมูลส่วนบุคคล พ.ศ. 2565** ข้อ 4(6)(ก) ระบุ need-to-know/least privilege และ (ง) audit trails สำหรับการเข้าถึง/เปลี่ยน/ลบ. เป็นหลักฐานของ control ไม่ได้บังคับให้ใช้ schema ตามรายงานนี้ ([สำเนาราชกิจจานุเบกษาบนกรมที่ดิน, PDF หน้า 2–3](https://www.dol.go.th/media/813280155698073600/migration/2025/10/3V7jb2avm6ABNef4EDuth5Y1.pdf)). ตัว พ.ร.บ. จากราชกิจจานุเบกษา fetch ได้ 403 ในรอบนี้ จึงไม่อ้างว่าตรวจ original act ครบ; directory official ใช้อ้างที่มาเพิ่มเติมได้ ([กรมที่ดิน PDPA](https://www.dol.go.th/pdpa)). การตรวจข้อกฎหมายอื่น/ประกาศแก้ไขครบชุดยัง *unverified*.

HubSpot มี property-value history export พร้อมเวลาและแหล่งเปลี่ยน เป็นแบบอย่างแยก change history ออกจาก record updatedAt; อย่านำ retention ของ vendor มาใช้แทน retention policy ของ firm ([HubSpot property history](https://knowledge.hubspot.com/properties/export-property-history)).

### Export/import และ document merge

- [ ] CSV export เลือก columns จาก definitions ที่มีสิทธิ์; human header เป็น label พร้อม stable ID, machine contract มี definition revision/type/option IDs และ schema manifest. วันที่ ISO, boolean ชัด, ไม่ format number จน round-trip ไม่ได้; sensitive export ต้อง explicit.
- [ ] CSV import มี mapping preview, row errors, existing-case match policy, permissions/tenant/applicability check, idempotent batch; blank = unchanged โดย default, clear ต้อง explicit. Unknown option ไม่ auto-create และไม่สร้าง schema ใหม่จาก CSV headers โดยไม่ review.
- [ ] Escape CSV separator/quotes/newlines และ spreadsheet formula-leading values; แยก human spreadsheet-safe export กับ machine round-trip contract เพราะ OWASP ระบุว่าไม่มี sanitization universal สำหรับทุก spreadsheet consumer ([OWASP CSV Injection](https://community.owasp.org/attacks/CSV_Injection)).
- [ ] Template tokens อ้าง stable field ID/key; selector แสดง label/type/group; render resolver ตรวจ field read/use permission และ safe escaping ตาม engine. ไม่ส่ง JSON ทั้งก้อนเป็น unrestricted merge variable.
- [ ] Missing/hidden/archived field policy ชัด: preview ระบุ missing fields, ห้าม fabricate empty sensitive value ว่าเคยมี; generated document เก็บ rendered snapshot + definition revision เพื่อ reproducibility และไม่เปลี่ยนย้อนหลังเมื่อ rename.

Clio Draft มีชื่อ mapping แบบ case-sensitive และเตือนว่า rename หลัง sync อาจกระทบ mapping เป็นเหตุผลเชิงผลิตภัณฑ์ให้ของเราแยก immutable token จาก label; ไม่ได้แปลว่าทุก Clio Manage integration ใช้ชื่อเป็น key ([Clio Draft mapping](https://help.clio.com/hc/en-150/articles/24317070863899-Clio-Draft-Draft-and-Manage-Documents)).

### API / MCP และ definition evolution

- [ ] REST definitions discovery เห็นเฉพาะ metadata ที่อนุญาต; values patch ใช้ immutable field IDs + expected case/definition revision; omitted = unchanged, explicit clear = remove key, unknown/retired new assignment = field-specific error; no type coercion แบบเงียบ.
- [ ] Canonical empty semantics: SQL NULL = legacy/no document, missing key = no answer, JSON null = legacy explicit null ที่ต้องระบุ policy; writer ใหม่ใช้ remove-key เพื่อ clear; empty text ไม่เท่ากับ false/0. Prisma `DbNull/JsonNull/AnyNull` ใช้ให้ถูก ไม่ใช้ truthy check เป็น required validator ([Prisma v6 JSON null](https://www.prisma.io/docs/orm/v6/prisma-client/special-fields-and-types/working-with-json-fields#using-null-values)).
- [ ] Rename/reorder ไม่แก้ value; archive field/option อ่านข้อมูลเก่าได้แต่ห้ามใช้เติมค่าใหม่; การเปลี่ยน existing value ของ archived field ต้อง explicit restore หรือ controlled migration. เปลี่ยน type ที่มี data ใช้ new definition + mapped conversion ไม่แก้ความหมายย้อนหลัง.
- [ ] Definition publish ตรวจ dependency (templates/reports/filters/import mappings/automations), revisions และ affected cases; new required แสดง completeness debt ไม่บังคับให้ทุก historical record ถูกกรอกในครั้งเดียว.
- [ ] MCP discovery/read/filter/write เมื่อเปิดต้องเรียก policy+validator เดียวกับ REST และตรวจสิทธิ์ทุก invocation; ไม่ return entire JSON อัตโนมัติ; AI summary เดิมต้องปรับ projection ก่อน sensitive field rollout. MCP protocol security ไม่ได้สร้าง field ACL ให้เอง; audience validation/token passthrough rules เป็นคนละชั้น ([MCP security best practices](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)).
- [ ] Acceptance scenarios: same key ต่าง firm, role denied ทุก output, 0/false required, invalid date/number/option, schema race, concurrent writers ต่าง key, explicit clear, archived option still readable, CaseType change preserve values, CSV round-trip, internal cost key retained, template permission และ migration retry/rollback. นี่คือรายการทดสอบสำหรับ implementation ในอนาคต ยังไม่ได้รันในงานวิจัย.

## Open questions สำหรับ owner

1. “Custom Fields” รุ่นแรกให้ใช้เฉพาะ Case หรือจำเป็นต้องมี Contact/Company/Job ด้วย? เสนอ Case ก่อน โดย metadata แยก entityKind รอขยาย ไม่แชร์ values ข้าม entity.
2. เจ้าของ firm กับ OFFICE_MANAGER ควรเพิ่ม field/เปลี่ยน privacy ได้เท่ากันหรือไม่? capability เดิมให้ทั้งสองจัด firm content แต่ sensitivity policy อาจต้อง owner approval.
3. Required หมายถึงห้ามเปิด Case, ต้องครบก่อน advance, หรือก่อน stage เฉพาะ? เสนอ draft-friendly required-before-advance เป็น default ตาม behavior เดิม.
4. ต้องใช้ filter/sort/aggregate field ไหนในงานจริง? ขอ use cases ตัวอย่าง เช่น “ทุนประกันมากกว่า X”, “วันหมดอายุใน 30 วัน”, “จังหวัดในกลุ่ม Y”; ถ้า arbitrary reports ทุก field จำเป็นต้องเปลี่ยน architecture/phase.
5. ข้อมูลใดเป็น PII/sensitive, ใครอ่าน/แก้/export/merge/ส่ง AI ได้ และ policy อยู่กับ firm หรือ platform? มี portal-visible fields ใน MVP หรือไม่?
6. ต้องการ cap fields/options/bytes ต่อ firm เท่าไร และคิด entitlement เป็น core feature หรือแยก plan? ยังไม่มี evidence ทางธุรกิจให้เลือก cap/ราคา; ไม่ควร copy competitor limits เป็น capacity ของเรา.
7. Archive เก็บนานเท่าไร, ใคร restore/purge, legal hold ใช้อย่างไร? เสนอไม่ลบ values อัตโนมัติขณะยังไม่มี retention policy.
8. ลูกค้าเดิมมี arbitrary JSON keys ที่สร้างโดย manual DB/import/integrations กี่ชุด? ต้อง inventory production ก่อน final migration mapping.
9. Definition ใหม่ควรนำไปใช้กับ historical cases ทันทีหรือเฉพาะ new cases? เสนอทุก case อ่านได้ตาม applicability แต่ new required ไม่ทำให้ unrelated edits ล้มเหลว.
10. ต้องรักษา API clients/mobile versions เก่านานเท่าไร และมี schema discovery/MCP integration ผู้ใช้จริงหรือยัง? ตัดสิน compatibility window ก่อนเปลี่ยน replacement PATCH.

### ผลตรวจข้อ 4 (Claude, 2026-11-14)

- **Built-in columns ไม่แตะ:** `Case` มีคอลัมน์จริงอยู่แล้ว เช่น `claimedAmount`, `estimatedFee`, `actualFee`, `courtName`, `courtLevel`, `blackCaseNumber`, `redCaseNumber`, `limitationDeadline`, `referralSource`, `customerRef`, `subType`, `partyRole` (`apps/api/prisma/schema.prisma`, `model Case`) — custom field ห้ามซ้ำหรือแทนที่ field เหล่านี้
- **List filter ปัจจุบัน** (`CaseQueryDto`, `apps/api/src/cases/dto/case.dto.ts:458`) มีแค่ `stage`, `party`, `userId`, `status`, `search` — filter ตาม custom field เป็นของใหม่ทั้งหมด ไม่กระทบของเดิม
- **System keys ที่ใช้ใน `customFields` อยู่แล้ว** ต้องจองไว้ ห้าม user สร้าง key ซ้ำ: `incidentDate`, `estimatedDamage` (เขียนโดย intake, `apps/api/src/intake/intake.service.ts:1294`), `chargeSection`, `prosecutor` (default `fieldSchema` คดีอาญา, `packages/shared/src/index.ts`; อ่านใน `apps/api/src/cases/case-info.ts:30`)
- **ข้อมูล local DB** (อ่านอย่างเดียว): 169 cases มีแค่ key `estimatedDamage` (5) และ `incidentDate` (5); 54 จาก 250 `CaseType` มี `fieldSchema` — **ยังไม่ได้ตรวจ production** ต้อง inventory ก่อนทำ migration จริง
- **ข้อสรุป:** design แบบเพิ่มอย่างเดียวทำได้ — คอลัมน์เดิม, filter เดิม และ system keys ไม่เปลี่ยน; field ใหม่ใช้ ID ของตัวเองใน namespace แยกจาก system keys
