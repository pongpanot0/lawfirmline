# Requirements รวม: Customer Portal (รับ–ส่งงาน + ประวัติที่เผยแพร่)

วันที่: 5 กันยายน 2569
สถานะ: เอกสารสรุปรวมสำหรับวางแผนพัฒนา รวมและประสาน requirements จาก 2 เอกสารก่อนหน้า ยังไม่ใช่การยืนยันว่าระบบมีความสามารถนี้แล้ว

เอกสารนี้รวม [operations-outlook-customer-portal-requirements.md](2026-09-05-operations-outlook-customer-portal-requirements.md) (#4) กับ [customer-portal-work-exchange.md](2026-09-05-customer-portal-work-exchange.md) (#5) เข้าด้วยกัน ตามที่ผู้ใช้ยืนยันว่า **#5 เป็นฟีเจอร์เสริมบน #4 ไม่ได้แทนที่** โครง Portal เดิมทั้งหมด

จุดที่เคยไม่ตรงกันระหว่างสองไฟล์ และคำตอบที่ยืนยันแล้ว:

| จุดที่ต้องยืนยัน | คำตอบที่ยืนยัน |
|---|---|
| เรื่องที่ลูกความส่งผ่าน Portal ไหลเข้าคิวรับเรื่องใด | ไหลเข้า **F01 Intake pipeline เดียวกัน** กับที่สำนักงานใช้รับเรื่องภายใน (ดูส่วน 3) |
| ลำดับ roadmap เปลี่ยนหรือไม่ เมื่อ Portal ต้องมี intake ตั้งแต่ต้น | **ไม่เปลี่ยนลำดับหลัก** ของ #4 (Outlook → Ops Hub → Portal) แต่เพิ่มความสามารถรับ-ส่งงานเข้าไปใน **ขั้น C** แทนที่จะรอถึงขั้น D (ดูส่วน 7) |

## 1. เป้าหมายรวม

- ลูกความไม่เห็นข้อมูลทั้งหมดของคดี เห็นเฉพาะสิ่งที่สำนักงานเลือกแชร์
- **(เพิ่มจาก #5)** ลูกความส่งเรื่องใหม่ ส่งงาน และส่งข้อมูลเพิ่มเติมผ่าน Portal ได้ — Portal จึงเป็นทั้งช่องทางรับ-ส่งงานและช่องทางดูประวัติ/ผลงาน
- เมื่อเปลี่ยนผู้ติดต่อ คนใหม่ดูประวัติรับ-ส่งและผลงานเก่าที่ได้รับอนุญาตได้ โดยไม่ต้องเปิดสำนวนภายในทั้งหมด และไม่ต้องเริ่มแฟ้มใหม่
- ลดการอธิบายงานย้อนหลังซ้ำ โดยเฉพาะรายงานปิดงานผ่าน Outlook (เชื่อมกับ requirement ผู้ช่วยร่างอีเมล — ดูส่วน 6)

## 2. โครงหน้าจอ Portal (รวม)

โครงหลักยึดตาม #4 โดยเพิ่มความสามารถส่งงานจาก #5 เข้าไปแต่ละหน้าที่เกี่ยวข้อง

| หน้า | สิ่งที่ลูกความเห็น/ทำได้ | ที่มา |
|---|---|---|
| หน้าหลัก (งานของฉัน/บริษัท) | คดีที่ตนมีสิทธิ อัปเดตล่าสุด นัดถัดไป สิ่งที่ต้องส่งให้ทนาย **+ ปุ่ม "ส่งเรื่องใหม่"** | #4 + #5 |
| รอฉันดำเนินการ | ข้อมูลที่ต้องส่ง คำถามที่ต้องตอบ ผลงานที่ต้องตรวจ พร้อมวันต้องการและลิงก์กลับไปยังเรื่อง | #5 |
| ภาพรวมคดี | ชื่อเรื่อง ขอบเขตงาน ผู้ติดต่อสำนักงาน สถานะปัจจุบันและคำอธิบายสั้น | #4 |
| กระบวนคดีและประวัติงาน | เหตุการณ์ที่เผยแพร่เรียงเวลา วันเกิดเหตุการณ์ สิ่งที่ทำ ผลที่ได้ ขั้นถัดไป (เลือกเผยแพร่เมื่อเหมาะกับเรื่อง ไม่ใช่เปิดประวัติภายในทั้งหมด) | #4 |
| งานที่สำนักงานดำเนินการ | ผลงานสำคัญ เช่น หนังสือบอกกล่าว ประชุม เจรจา ยื่นเอกสาร ไปนัด | #4 |
| นัดและสิ่งที่ต้องเตรียม | วัน เวลา สถานที่ ต้องเข้าร่วมหรือไม่ รายการเตรียมตัว | #4 |
| คำขอข้อมูล / ส่งข้อมูลเพิ่มเติม | เอกสาร/ข้อมูลที่สำนักงานขอ วันต้องการ สถานะส่ง-ได้รับ-ขอเพิ่ม **+ พื้นที่ข้อความรับ-ส่งและแนบไฟล์ภายในเรื่องเดียวกัน** | #4 + #5 |
| เอกสารและผลงาน | ฉบับที่เผยแพร่ให้ผู้ใช้นั้น พร้อมชนิด วันที่ เวอร์ชัน คำอธิบาย อ่าน/ดาวน์โหลดตามสิทธิ ย้อนกลับไปเรื่องต้นทางได้ | #4 |
| การตัดสินใจและข้อตกลง | ข้อเสนอที่เผยแพร่ ทางเลือก ผลตัดสินใจที่บันทึกไว้ ใครตัดสินใจและเมื่อใด | #4 |
| สรุปปิดงาน | ผลงานทั้งหมด ผลคดี งานที่เหลือ เอกสารส่งมอบ | #4 |
| ข้อมูลสำหรับผู้รับช่วงใหม่ | สรุปตั้งแต่เริ่ม ประวัติสำคัญ ข้อตกลงเดิม รายการที่ต้องทำต่อ | #4 |

### ภายในแต่ละเรื่องที่ลูกความส่ง (จาก #5)

1. รายละเอียดคำขอและไฟล์ที่ลูกความส่ง
2. สถานะที่เปิดเผยและสิ่งที่ต้องทำต่อ
3. ข้อความและไฟล์รับ-ส่ง
4. ความคืบหน้าที่สำนักงานเลือกเผยแพร่
5. ผลงานและรายงานปิดงาน

## 3. การรับงานฝั่งสำนักงาน — เชื่อมกับ F01 Intake pipeline

**ยืนยันแล้ว**: เรื่องที่ลูกความส่งผ่าน Portal ไม่ใช่คิวแยกต่างหาก แต่ไหลเข้า **F01 รับเรื่องและคัดกรอง** ([lawyer-features-ui-plan.md](2026-09-05-lawyer-features-ui-plan.md)) เดียวกันกับที่สำนักงานใช้รับเรื่องช่องทางอื่น (โทร/อีเมล/walk-in) เพื่อไม่ให้เกิดสองระบบคัดกรองที่ข้อมูลไม่ตรงกัน

เส้นทางรวม:

```
ลูกความส่งเรื่องผ่าน Portal ──┐
                              ├─→ F01 กล่องรับเรื่อง (คัดกรอง/ตรวจผลประโยชน์ขัดกัน) → ตกลงขอบเขต/ค่าจ้าง → รับดำเนินการและมอบหมาย → ส่งความคืบหน้า/ผลงาน → ปิดงาน
ช่องทางอื่น (โทร/อีเมล) ────────┘
```

ผลต่อการออกแบบข้อมูล:

- F01 ต้องมี field ระบุ **แหล่งที่มาของเรื่อง** (Portal / โทร / อีเมล / walk-in) เพื่อแยกช่องทาง แต่ **ใช้สถานะและ workflow เดียวกัน**
- เรื่องจาก Portal ต้องผ่านการตรวจผลประโยชน์ขัดกัน (F02) เหมือนเรื่องที่รับทางอื่น ไม่มีทางลัดเพราะมาจากลูกความเดิม
- "การส่งเรื่องสำเร็จ" (ลูกความได้เลขอ้างอิง) ≠ "สำนักงานตกลงรับดำเนินการแล้ว" — สถานะภายนอกที่ลูกความเห็นต้องแยกจากสถานะภายในของ F01 ชัดเจน (ดูตาราง status mapping ส่วน 4)
- แยก "วันที่ลูกความต้องการ" ออกจาก "วันที่สำนักงานตกลงส่งงาน" เป็นสอง field เสมอ

## 4. Status mapping — ภายในกับภายนอก

| สถานะภายใน (F01/Ops Hub) | สถานะภายนอกที่ลูกความเห็นบน Portal |
|---|---|
| เรื่องเข้าคิว ยังไม่ประเมิน | ส่งแล้ว |
| อยู่ระหว่างประเมิน/ตรวจผลประโยชน์ขัดกัน | สำนักงานรับเรื่องแล้ว |
| รอข้อมูลเพิ่มจากลูกความ | ขอข้อมูลเพิ่ม |
| กำลังตกลงขอบเขต/ค่าจ้าง | รอตกลงขอบเขต |
| ตกลงแล้ว มอบหมายทนาย | รับดำเนินการ |
| ทนายส่งผลงาน/ความคืบหน้า | ส่งผลงานแล้ว |
| ปิดแฟ้มหรือปิดงานย่อย | ปิดงาน |
| ปฏิเสธ/ส่งต่อ | ไม่รับดำเนินการ |

ชื่อสถานะและลำดับเป็นข้อเสนอสำหรับออกแบบรายละเอียด ไม่บังคับให้ทุกเรื่องผ่านทุกสถานะ (เรื่องบางประเภทอาจข้าม "รอตกลงขอบเขต" เช่นงานที่เชื่อมกับแฟ้มเดิมที่มีขอบเขตอยู่แล้ว)

## 5. การเลือกแชร์และสิทธิ (คงตาม #4 และ #5 — ไม่มีความขัดแย้ง)

- ข้อมูลภายในเป็นส่วนตัวโดยค่าเริ่มต้น ทนายต้องเลือกข้อความ เอกสาร และผู้รับก่อนเผยแพร่
- ไม่เปิดกลยุทธ์คดี บันทึกภายใน งานย่อยของทนาย ภาระงาน และ On hold ภายในทั้งหมด
- แยกข้อความ "ภายในสำนักงาน" กับ "ส่งให้ลูกความ" ชัดเจนใน UI พร้อมหน้าตัวอย่างก่อนเผยแพร่
- เอกสารที่แชร์ผูกกับฉบับที่เลือก การอัปโหลดร่างใหม่ไม่แทนที่ฉบับที่ลูกความเห็นเอง
- ประวัติรับ-ส่งและไฟล์ที่ลูกความส่งต้องมีสิทธิรายเรื่อง ไม่เปิดให้ผู้ติดต่อทุกคนเพียงเพราะอยู่บริษัทเดียวกัน
- การอ่าน/ดาวน์โหลดไม่เท่ากับอนุมัติผลงานหรือการตัดสินใจทางคดี

## 6. เชื่อมกับ Operations Hub และ Outlook (คงตาม #4/#5)

- Operations Hub เห็นผู้รับผิดชอบ ภาระงาน เหตุที่รอ ส่วนลูกความเห็นเฉพาะสถานะ/ข้อความที่เลือกเผยแพร่
- เมื่อขอข้อมูลจากลูกความผ่าน Portal ให้เชื่อมกับงานติดตามภายในได้ เมื่อได้รับคำตอบให้แจ้งผู้รับผิดชอบตรวจ ไม่ปิดงานว่าครบอัตโนมัติ
- รายงานปิดงานฉบับที่ทนายตรวจแล้วใช้เป็นข้อมูลสร้างร่างอีเมล Outlook และเลือกเผยแพร่ใน Portal ได้ (คนละการกระทำ)
- สร้าง Draft ใน Outlook / ส่งอีเมลแล้ว / เผยแพร่บน Portal เป็นคนละสถานะ

## 7. Roadmap รวม — ยืนยันแล้วว่าไม่เปลี่ยนลำดับหลัก

ยึดลำดับขั้น A→D ของ #4 โดยย้ายความสามารถ "รับ-ส่งงาน" จาก #5 เข้าไปอยู่ **ขั้น C** (แทนที่จะรอถึงขั้น D ตามที่ #4 เคยวางไว้)

### ขั้น A: ลดงานอีเมลปิดคดีให้เห็นผลก่อน
แบบบันทึกผล/ประวัติงานที่จำเป็น แม่แบบสรุปปิดงาน หน้าตรวจสองฝั่ง คัดลอกหรือสร้าง Draft ใน Outlook

### ขั้น B: Operations Hub ที่ใช้ข้อมูลเดียวกัน
สถานะงาน ผู้รับผิดชอบ On hold พร้อมเหตุและวันติดตาม ตารางภาระงาน รายการต้องจัดการ

### ขั้น C: Portal — ประวัติ + รับ-ส่งงาน (รวมจาก #4 + #5)
- เข้าระบบตามคำเชิญและสิทธิรายเรื่อง
- **(ย้ายจากขั้น D เดิม)** ส่งเรื่องใหม่และแนบไฟล์ → เชื่อม F01 ตามส่วน 3
- **(ย้ายจากขั้น D เดิม)** กล่องรับงานฝั่งสำนักงานและการมอบหมาย (ส่วนภายในของ F01)
- **(ย้ายจากขั้น D เดิม)** สถานะภายนอกและข้อความ/ไฟล์รับ-ส่งในเรื่องเดิม
- ภาพรวม Timeline รายงาน/เอกสารที่อนุมัติ
- การส่งต่อผู้ติดต่อพร้อมสิทธิย้อนหลัง
- เลือกเผยแพร่ผลงาน เอกสาร และรายงานปิดงาน
- ค้นย้อนหลังและให้สิทธิผู้ติดต่อใหม่

### ขั้น D: เพิ่มการโต้ตอบ (ขอบเขตที่เหลือหลังยืนยันความจำเป็น)
- นัดหมายผ่าน Portal โดยตรง (ปัจจุบันดูผ่าน Portal ได้ แต่ยังไม่รับ input จากลูกความ)
- บันทึกรับทราบ/การตัดสินใจตามขอบเขตที่ตกลง
- ข้อมูลการเงินที่เลือกเผยแพร่ (ใบแจ้งหนี้/การชำระ)
- Outlook Add-in และการซิงก์อีเมลส่งจริง (Sent Items) — พิจารณาหลังยืนยันสิทธิ/นโยบายบัญชี Outlook

ยังไม่จำเป็นต้องเปิดทุกขั้นตอนศาล ทุกข้อมูลการเงิน หรือเชื่อม Outlook โดยตรงในรุ่นเดียวกัน

## 8. เมื่อเปลี่ยนผู้ติดต่อ — คงรายละเอียด 3 สถานการณ์ของ #4

#5 ย่อขั้นตอนไว้แบบง่าย แต่ #4 มีรายละเอียดที่ควรเก็บไว้ใช้จริง คือแยก 3 สถานการณ์ไม่ให้ใช้ workflow เดียวกันหมด:

| สถานการณ์ | การจัดการ |
|---|---|
| คนติดต่อเปลี่ยน แต่ลูกความเดิม | ตรวจผู้มีอำนาจยืนยัน แล้วให้สิทธิตามแฟ้มและรายงานที่อนุมัติย้อนหลัง |
| เพิ่มผู้เกี่ยวข้อง เช่น ฝ่ายการเงินหรือผู้บริหาร | ให้สิทธิเท่าหน้าที่ ไม่ถือว่าต้องเห็นทุกคดีหรือทุกการตัดสินใจ |
| เปลี่ยนตัวลูกความจริง เช่น โอนสิทธิ เปลี่ยนนิติบุคคล หรือมีผู้จัดการแทนรายใหม่ | ให้สำนักงานตรวจฐานะและสิทธิเป็นกรณีเฉพาะก่อน ไม่ย้ายสิทธิประวัติทั้งหมดอัตโนมัติ |

ขั้นตอนส่งต่อ (รวมจาก #4 และ #5 ไม่ขัดกัน):

1. สำนักงานตรวจผู้มีอำนาจยืนยันการเปลี่ยนผู้ติดต่อ
2. เลือกลูกความ แฟ้ม และสิทธิของผู้รับช่วง (ทั้งหมดที่อนุมัติ / ตั้งแต่วันที่กำหนด / เฉพาะรายการที่เลือก)
3. ตรวจรายการที่เคยเผยแพร่เฉพาะบุคคล ไม่เปิดให้คนใหม่เพียงเพราะสังกัดองค์กรเดียวกัน
4. สร้างสรุปส่งต่อจากข้อมูลที่คนใหม่มีสิทธิอ่านเท่านั้น
5. เชิญบัญชีคนใหม่ ให้ยืนยันตัวตน บันทึกผู้อนุมัติและวันเริ่มสิทธิ
6. ถอน/ปรับสิทธิคนเดิมตามที่ตกลง รวม session และลิงก์เข้าใช้งานที่ระบบควบคุมได้ — ประวัติเก่ายังเก็บชื่อผู้ส่ง/ผู้ตัดสินใจเดิมไว้
7. เก็บประวัติการเปลี่ยนสิทธิ การอ่าน/ดาวน์โหลดตามที่ระบบบันทึกได้

ไม่ใช้บัญชีเดิมร่วมกัน ไม่แก้ชื่อคนใหม่ทับประวัติคนเก่า รุ่นแรกให้สำนักงานเป็นผู้จัดการคำเชิญและสิทธิเอง (ยังไม่เปิดให้ผู้ดูแลองค์กรลูกค้าเชิญคนเอง)

## 9. เกณฑ์ตรวจรับ (รวมจาก #4 + #5 ไม่ให้ตกหล่น)

1. ลูกความส่งเรื่องได้เลขอ้างอิง และสำนักงานเห็นเรื่องในคิว F01 โดยไม่ถือว่ารับว่าจ้างแล้ว
2. วันที่ต้องการของลูกความแยกจากวันที่สำนักงานตกลง
3. ข้อความและไฟล์เพิ่มเติมอยู่ในเรื่องเดิม พร้อมผู้ส่งและเวลา
4. ผู้รับเห็นเฉพาะสถานะ ข้อความ และฉบับเอกสารที่อนุญาต ไม่เห็นข้อมูลภายในผ่านหน้าจอหรือการเรียกข้อมูลโดยตรง
5. ผู้ติดต่อใหม่เห็นงานย้อนหลังตามสิทธิ รวมงานปิดแล้ว โดยไม่เห็นทุกแฟ้มขององค์กรอัตโนมัติ
6. ถอนสิทธิคนเดิมแล้วหยุดการเข้าถึงในระบบและลิงก์ที่ระบบควบคุมได้ทันที โดยประวัติเก่ายังอยู่ (แต่ไฟล์ที่ดาวน์โหลดไปแล้วหรืออีเมลที่ส่งไปแล้วเรียกคืนไม่ได้)
7. การเผยแพร่ผลงานไม่เท่ากับลูกความยอมรับหรือปิดเรื่อง ต้องบันทึกผลแยกกัน
8. รายงานสรุปให้ผู้ติดต่อใหม่ไม่รวมข้อเท็จจริงจากเอกสารที่ผู้ติดต่อนั้นไม่มีสิทธิอ่าน
9. ข้อมูลการตัดสินใจเดิมยังระบุผู้ตัดสินใจและวันที่เดิมหลังเปลี่ยนผู้ติดต่อ
10. การปิดงานสำนักงานไม่ทำให้ระบบแสดงว่าคดีถึงที่สุดหรือบังคับครบแล้วหากยังไม่มีข้อมูลยืนยัน

## 10. ข้อมูลที่ยืนยันแล้ว (อัปเดต 5 กันยายน 2569)

| คำถาม | คำตอบที่ยืนยัน | ผลต่อการออกแบบ |
|---|---|---|
| บัญชี Outlook เป็นแบบใด | **Outlook.com** (ไม่ใช่ Microsoft 365 องค์กร) กล่องส่วนตัวรายทนาย | ใช้ Microsoft Graph กับบัญชี Outlook.com (personal/consumer) — ตรวจสิทธิ OAuth consumer flow แยกจาก M365 tenant app registration ที่ #4 เคยตั้งสมมติฐานไว้ ไม่มี admin consent ระดับองค์กรให้พึ่งพา |
| ข้อมูลกระบวนคดีปัจจุบันอยู่ที่ไหน | **เอกสารและอีเมล** ไม่ใช่ในระบบ | ประวัติเดิมต้อง **นำเข้าหรือให้ทนายสรุปครั้งแรก** ก่อนเปิดใช้ผู้ช่วยร่างอีเมล/Portal — งานสรุปประวัติย้อนหลังเป็น task แยกที่ต้องวางแผนเวลา ไม่ใช่ auto-migrate |
| ผู้อนุมัติเผยแพร่ Portal | **ทนายเจ้าของคดีคนเดียว** ไม่มีชั้นตรวจเพิ่ม | ไม่ต้องออกแบบ approval workflow หลายขั้น พอมี single-approver + audit log ว่าใครอนุมัติเมื่อใด |
| ทนายเห็นแฟ้มลูกความองค์กรเดียวกันแค่ไหน | **เห็นทุกแฟ้ม** ขององค์กรลูกความนั้น | สิทธิทนายอยู่ระดับ "องค์กรลูกความ" ไม่ใช่ระดับ "แฟ้มที่รับมอบหมาย" — ต่างจากสิทธิฝั่งผู้ติดต่อลูกค้า (ส่วน 8) ที่ยังคงจำกัดตามที่อนุมัติเป็นรายแฟ้ม |
| แยกฝ่ายกฎหมาย/การเงินของลูกความโดยดีฟอลต์ไหม | **แยกออก** | ผู้ติดต่อฝ่ายการเงินไม่เห็นเนื้อหาคดีโดยดีฟอลต์ และผู้ติดต่อฝ่ายกฎหมายไม่เห็นข้อมูลใบแจ้งหนี้/การชำระโดยดีฟอลต์ ต้องให้สิทธิข้ามฝ่ายเป็นรายกรณี |
| ใครอนุมัติเปลี่ยนผู้ติดต่อ | **สำนักงานอนุมัติ** | ตรงกับขั้นตอนส่งต่อผู้ติดต่อในส่วน 8 ข้อ 1 อยู่แล้ว (สำนักงานตรวจผู้มีอำนาจยืนยัน) — ยืนยันว่าไม่ต้องมีขั้นตอนให้ลูกความ self-service อนุมัติเอง |

| ช่องทางแจ้งเตือนผู้ติดต่อ | **อีเมลและ LINE** | ต้องรองรับสองช่องทาง — เก็บการตั้งค่าช่องทางที่ผู้ติดต่อแต่ละคนเลือกรับ และผูก LINE ID เข้ากับบัญชีผู้ติดต่อ (ต้องออกแบบขั้นตอนผูกบัญชี LINE แยกต่างหาก) |
| นโยบายอายุสิทธิและการเก็บประวัติ | **เก็บตลอดไป** ไม่มีวันหมดอายุ/archive อัตโนมัติ | ประวัติรับ-ส่ง เอกสารที่เผยแพร่ และ log การอ่าน/ดาวน์โหลด เก็บถาวรในระบบ ไม่ต้องออกแบบ retention/auto-purge job |
| ลูกความลบ/เรียกคืนเรื่องที่ส่งแล้วได้หรือไม่ | **Soft delete** — ลูกความ "ลบ" ได้จากมุมมองตน แต่ฝั่งทนายยังเห็นเรื่องเดิมพร้อมป้าย **"ไม่ได้ใช้"** ไม่ใช่การลบจริง | ต้องมี field สถานะ `withdrawn_by_client` (หรือเทียบเท่า) แยกจากการลบข้อมูลจริง เพื่อไม่ให้ประวัติหายจากฝั่งสำนักงาน แม้ลูกความ "ลบ" ไปแล้ว |

คำถามทั้งหมดในส่วนนี้ได้รับคำตอบครบแล้ว ไม่มีคำถามเปิดที่บล็อกการออกแบบเหลืออยู่

## 11. ผล Feasibility Review: Microsoft Graph กับ Outlook.com (ยืนยันแล้ว — ไม่มี blocker)

ตรวจสอบโดย backend-reviewer วันที่ 5 กันยายน 2569:

- **Graph API ใช้ได้กับ Outlook.com จริง** — endpoint `POST /me/mailFolders/drafts/messages` รองรับ personal Microsoft Account ไม่ต่างจาก M365
- **OAuth**: ต้องใช้ `/consumers` endpoint แทน tenant-specific endpoint — **ทนายแต่ละคนต้อง consent สิทธิ์ `Mail.ReadWrite` เอง** ไม่มี admin อนุมัติรวมทีเดียวแบบองค์กร
- **⚠️ Shared mailbox ใช้ไม่ได้** — สอดคล้องกับที่ยืนยันไว้แล้วว่าใช้กล่องอีเมลส่วนตัวรายทนาย ไม่มีปัญหา
- **ไม่มีข้อจำกัดเรื่อง throttling/quota/app verification** ที่จะกระทบสำนักงานขนาดเล็ก-กลาง และไม่มีค่าใช้จ่ายเพิ่ม (Graph API ฟรี)

**แผนพัฒนาที่แนะนำ (ปรับจากขั้น A เดิม)**:
1. **Phase 1**: Copy-to-clipboard ก่อน (ทดสอบคุณภาพ template โดยไม่ต้องทำ OAuth)
2. **Phase 2**: เพิ่ม Graph API + OAuth จริง (ทนาย consent ครั้งเดียวต่อคน)
3. **Phase 3 (ถ้าจำเป็น)**: Outlook Add-in — ไม่จำเป็นสำหรับ MVP

**ยืนยันแล้ว (5 กันยายน 2569)**: ทนายทุกคนมีบัญชี Outlook.com ใช้งานอยู่จริง และสำนักงานยอมรับให้ข้อมูลอยู่บน Outlook.com cloud ได้ — ไม่มีเงื่อนไขค้างก่อนเริ่ม Phase 2
