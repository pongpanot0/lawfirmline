# Mobile: เปิดแล้วรู้ว่าทำอะไรต่อ

ออกแบบวันที่ 2 ตุลาคม 2026 จาก source ใน worktree `11b5/lawfirm` และ flow ลูกค้า → คดี → SOP → งาน → ส่งตรวจ ที่เพิ่งปรับบนเว็บ รอบนี้เป็นข้อเสนอและต้นแบบ ยังไม่ได้เปลี่ยนแอป Expo หรือปล่อย native build

## แบบที่แนะนำ

ตามข้อกำหนดล่าสุด **คง UI มือถือเดิมให้มากที่สุด**: แท็บ สี ฟอนต์ การ์ด ปฏิทิน ทีม และ Court Day เดิม ปรับลำดับข้อมูลในหน้าวันนี้ เพิ่มทางเข้าทำงาน และแยกตามบทบาท ใช้ **A — งานวันนี้** เป็นการปรับหน้าเดิม ส่วน B/C ใช้เปรียบเทียบการเข้าผ่านคดีและนัดหมาย ไม่เสนอเปลี่ยนหน้าหลักทั้งแอป

**ปรับตามคำทักเรื่องเจ้าของ:** ต้นแบบรอบแรกย่อหน้าเจ้าของเหลือคิวงานมากเกินไป รอบนี้คืนโครงหน้าวันนี้ตาม `apps/mobile/app/(tabs)/index.tsx`: กำลังคน → งานครบกำหนดของทีม → นัดของสำนักงาน → ชุดเบิก → สถิติ → เกินกำหนด/คำเตือน → ทางลัดเดิม และเพิ่มรายการรอฉันตรวจ เจ้าของใช้หน้าเดิมนี้ทุก variant ไม่สลับเป็นหน้า Court Day หรือแฟ้มคดีทั้งหน้า ทางเข้าคดี/ปฏิทินยังอยู่ในแท็บเดิม

เจ้าของเห็นจำนวนคน นัดศาล วันลา งานค้างและเกินกำหนดรายคน พร้อมคำเตือนงานตรงวันลา; ไม่ตีความว่าไม่มีงานบันทึกแล้วเท่ากับว่าง เพิ่มเฉพาะปุ่มเปิดงานรายคน ปุ่มรอฉันตรวจ/เกินกำหนด และตัวกรองงานทีม/รอรับงาน ปุ่มชุดเบิกรออนุมัติ/รอจ่ายเปิดรายการที่กรองแล้วด้วยจำนวนและยอดจากชุดเดียวกัน ต้นแบบแสดงรายการ/ทางเข้ารายละเอียด ไม่จำลองการอนุมัติหรือจ่ายเงินจริง

ข้อมูลเจ้าของใช้ของเดิม: `/dashboard/workload`, `/agenda/my-day`, `/calendar/events` ผ่าน calendar hook, `/leaves`, `/expense-claims`, `/dashboard/stats` และ `/agenda/actions` ไม่มี API สถิติอีกชุด ข้อมูลต้องอยู่ในสำนักงานที่เลือก เมื่อโหลดไม่สำเร็จให้แสดงสถานะโหลด/ผิดพลาดหรือข้อมูลล่าสุดตามรูปแบบเดิม ไม่แทนด้วยเลขศูนย์

เมนูหลักคงเดิม: **วันนี้ / คดี / ปฏิทิน / งาน / ทีม** เมนูเพิ่มเติมและแจ้งเตือนอยู่ในตำแหน่งหัวหน้าเดิม รายละเอียดภายในทีมและการทำรายการขึ้นกับสิทธิ์ ไม่มีการย้ายปฏิทินหรือทีมออกจากแท็บ

ต้นแบบกดทดลองได้:

- [A — คิวงานวันนี้](http://localhost:3018/?variant=A)
- [B — แฟ้มคดี](http://localhost:3018/?variant=B)
- [C — วันไปศาล](http://localhost:3018/?variant=C)

ตัวเลือกบทบาทในแถบต้นแบบใช้ได้ทั้งจอใหญ่และจอแคบ มีครบ 4 บทบาท เจ้าของคงหน้าเดิม ส่วนบทบาทอื่นสลับ A/B/C ด้วยปุ่มลูกศรเพื่อเทียบทางเข้าทำงานได้ ข้อมูลตัวอย่างอยู่ในหน่วยความจำ เริ่มใหม่ได้ด้วย reload

| --- | --- | --- | --- |
| OWNER — เจ้าของ | กำลังคน/ใครทำอะไร วันลา งานครบกำหนด นัดสำนักงาน ชุดเบิก สถิติคดี งานเกินกำหนด คำเตือน และรอฉันตรวจ | คงส่วนเดิม เปิดงานรายคน/กรองงานทีม/รอรับงาน เปิดผล/ไฟล์ก่อนตรวจหรือส่งกลับ ชุดเบิกเปิดตามสถานะเดิม | ข้อมูลเฉพาะสำนักงานตนเอง; ใช้การอนุมัติค่าใช้จ่ายเดิมและข้อมูลวันลา ไม่เอาสิทธิ์การเงินไปให้ role อื่น |
| SENIOR_LAWYER — Senior | งานรอตรวจที่รับตรวจได้ ทีม/คดีที่ดูแล และงานของตน | ตรวจผลก่อนกดผ่าน ส่งกลับพร้อมเหตุผล มอบหมาย/ติดตามงานภายในสิทธิ์ | Senior ไม่ใช่ Owner; ไม่แสดงอนุมัติการเงิน ตั้งค่าสำนักงาน หรือทุกคดีโดยอัตโนมัติ |

แยก **สิทธิ์เห็น / สิทธิ์แก้ / สิทธิ์มอบหมาย / สิทธิ์ตรวจ** ออกจากกัน คดีที่เห็นต้องผ่าน case-access ของ API ผู้รับผิดชอบ/ผู้สร้าง/ผู้ส่งตรวจต้องยังเปิดงานได้ตามสิทธิ์เดิม การซ่อนปุ่มเป็น UX เท่านั้น ผู้ไม่มีสิทธิ์ยิง API โดยตรงต้องถูกปฏิเสธด้วย

ข้อเท็จจริงจาก source: เมื่อสร้างงาน API ปัจจุบันตรวจการมอบหมายคนอื่นด้วยกฎ Owner/Senior ตามลำดับบทบาท แม้การสร้างนั้นมี caseId; การเปลี่ยนผู้รับผิดชอบงานในคดีใช้กฎ Lead/Owner และการตรวจขึ้นกับผู้ตรวจ/เงื่อนไขคดี จึงต้องตรวจเป็นรายคำขอ ไม่ใช้กฎเดียวว่า “Senior ทำได้ทุกอย่าง” หรือ “Lawyer ตรวจไม่ได้ทุกกรณี”

## คนใหม่ทำงานประจำได้ และเจ้าของเลือกคนจากงานวันนี้

เป้าหมายล่าสุดคือคนใหม่เปิดงานแล้วทำงาน routine ได้โดยไม่ต้องถามวิธีทำซ้ำ และ Owner รู้ว่าแต่ละคนทำอะไรอยู่ ติดอะไร ก่อนมอบหมายงานเพิ่ม คงหน้าวันนี้ รายชื่อทีม ฟอร์มงาน และเส้นทางส่งตรวจเดิม เพิ่มข้อมูลในจุดที่ตัดสินใจหรือทำงาน ไม่มีหน้าบทเรียน/ระบบอบรมอีกชุด

**ฝั่งคนทำ:** งานประจำที่สำนักงานกำหนดมีผลที่ต้องส่ง วิธีทำเป็นข้อ ไฟล์ต้นทางที่เปิดได้ ตัวอย่างผลงาน/ชื่อไฟล์ เกณฑ์ตรวจ และผู้รับตรวจติดมากับ task ID เดิม ไม่ต้องค้น SOP เอง คดี ผู้รับผิดชอบ และผู้ตรวจเติมจากบริบท งานทั่วไปยังเริ่มจากชื่ออย่างเดียว ไม่บังคับ checklist งานประจำกับทุกงาน

ต้นแบบใช้ตัวอย่าง “ถ่ายเอกสารแนบและตรวจชื่อไฟล์”: รับงาน → เปิดต้นฉบับ → แนบ PDF → ตรวจชื่อและทุกหน้า → ส่งให้ Senior ตรวจ; จำนวน 5 หน้าเป็นข้อมูลตัวอย่างของงานนี้ ไม่ใช่ข้อบังคับเอกสารทุกคดี บันทึกเพิ่มเติมกางเมื่อใช้ การติ๊กวิธีทำไม่ปิดงานหรือให้สิทธิ์อนุมัติเอง เมื่อส่งกลับ ให้เห็นเหตุผลก่อนวิธีทำและตรวจผลงานใหม่ก่อนส่งซ้ำ

หากติดขัด มีทาง “เอกสารขาด / ไม่แน่ใจ” ในงานเดิม บันทึกว่า **ทำแล้ว / เหลืออะไร / ติดอะไร** พร้อมเวลา เพื่อให้ผู้ดูแลงานเปิดเห็น ไม่สร้างงานใหม่แทนงานเดิมหรือส่งข้อความโดยอัตโนมัติ ปัญหาที่ยังไม่แก้และผลที่ยังไม่ครบต้องมีคำอธิบายว่าต้องทำอะไรต่อก่อนส่ง

**ฝั่ง Owner:** เพิ่ม “เทียบคนก่อนมอบหมาย” ในหน้าเดิม รายคนเห็นงานวางแผน/ครบกำหนดวันนี้ งานค้าง เกินกำหนด คิวตรวจ รอรับงาน เสร็จวันนี้ รายงานทำแล้ว/ทำต่อ จุดติดขัด เวลาอัปเดต นัดพร้อมเวลาและวันลา กดมอบหมายให้คนนั้นได้โดยคงชื่อ/รายละเอียดที่กรอกไว้ เมื่อเพิ่มงานวันนี้ คิวของคนที่รับต้องเพิ่มตามจริง

แยกคิวทำกับคิวตรวจ และใช้ worker ID เดิมหลังส่งตรวจเพื่อไม่ให้ปริมาณงานของผู้ทำย้ายไปนับเป็นการทำงานของผู้ตรวจ งานที่ไม่มีรายงานวันนี้ให้ขึ้น “ยังไม่มีข้อมูลวันนี้” รายงานวันก่อนให้แสดงวันที่จริงและจัดว่าไม่ครบของวันนี้ นัดไม่ทราบเวลาสิ้นสุดต้องไม่สรุปว่าบ่ายว่าง คิวศูนย์ไม่เท่ากับพร้อมรับงาน เวลา/จำนวน/แต้มเป็นข้อมูลประกอบการเลือก ไม่อ้างเป็นเปอร์เซ็นต์ความพร้อมหรือชั่วโมงที่ไม่ได้บันทึก

แอปจริงใช้ `GET /operations/daily?date=YYYY-MM-DD` ซึ่งเป็น Owner-only และมี `members.workTypes`, วันลา, นัด, `workerId`, `scheduledFor`, `completedAt`, `latestUpdate`, `blocker`, `holdReason`, `blockedBy` อยู่แล้ว `/dashboard/workload` เดิมยังใช้สรุปงานค้าง ใช้ `assignmentCandidates` จาก `apps/web/src/lib/daily-workboard.ts` ต่อ โดยย้ายส่วนบริสุทธิ์ไป shared เมื่อทำ native แทนเขียนการจัดอันดับอีกชุด ตัวช่วยเดิมพิจารณาวันลา ประเภทงานที่ตั้งไว้ ความครบของรายงาน และแต้มคิวตามขนาดงาน ไม่แปลว่าเป็นเวลาว่างแน่นอน

ข้อมูลของวันที่จะมอบหมายต้องโหลดใหม่เมื่อเปลี่ยนวัน; โหลดไม่ได้ให้บอกว่าเทียบคิวไม่ได้และคงร่าง เมื่อเลือกคนที่ลา มีนัด คิวหนัก ไม่ตรงประเภทงาน หรือข้อมูลไม่ครบ ให้แสดงสาเหตุและใช้การยืนยันเงื่อนไขแบบฟอร์มเว็บเดิม ไม่เลือกคนหรือย้ายงานเดิมให้เอง ต้นแบบรอบนี้มีข้อมูลเฉพาะ 2 ต.ค. และเปรียบเทียบจำนวน/รายงาน/นัด/ลา ยังไม่ได้จำลองทุกขนาดงานหรือคำนวณเวลาว่าง

**ขอบเขตที่ source ยังไม่รองรับ:** `PlaybookStep.instructions` ถูกคัดลอกลง `Task.description` และผูก release ด้วย label แล้ว จึงเริ่มแสดงวิธีทำใน task เดิมได้ แต่ Step DTO ปัจจุบันยังไม่มี expected output, source/example references หรือเกณฑ์ตรวจแบบมีชนิด และ Task ยังไม่มี progress ของ checklist นี้ การติ๊ก/เงื่อนไขก่อนส่งในต้นแบบอยู่ในหน่วยความจำเท่านั้น ก่อนบังคับใน native ต้องเพิ่มข้อมูลวิธีทำ/เกณฑ์ที่มี snapshot ของรุ่นและ step ให้ task เดิม บันทึก progress ตามสิทธิ์ task และตรวจผล/ไฟล์/สถานะที่ API ด้วย ไม่แยกเป็นระบบงานใหม่และไม่บังคับเพิ่มกับงานเก่าที่ไม่มีข้อกำหนด

SOP ของ routine ต้องเป็นวิธีที่สำนักงานตรวจและกำหนดไว้ ทนาย/Senior/Owner เตรียมชุดบนหน้าจัดการ SOP เดิมครั้งเดียว คนใหม่ใช้ซ้ำตามงานที่ได้รับ ไม่เดาวิธีทำหรือเกณฑ์ผ่านจากชื่อ task และไม่ปรับวิธีของงานที่กำลังทำตาม SOP รุ่นใหม่โดยเงียบ ๆ

## ใช้ของเดิมต่อ

ใช้ `FormPage`, `Dropdown`, `DatePicker`, `Attachments`, `ReassignSheet`, `CasePicker`, `QuickAdd` และตัวส่งคำขอ/ต่ออายุ session เดิม ไม่เพิ่มชุดฟอร์มหรือระบบไฟล์อีกชุด

ใช้สีและเป้าสัมผัสจาก `apps/mobile/src/theme.ts`: พื้น `#F6F7F9`, น้ำเงิน `#182B49`, ข้อความ `#232B38`, เส้นแบ่ง `#E3E7EE`, ทอง `#7C5A1E`; หัวข้อ Anuphan ตัวอ่านฟอนต์ระบบ เป้าสัมผัสอย่างน้อย 44 จุด ปุ่มหลักอยู่เหนือเมนูล่างและคีย์บอร์ด ชื่อคดียาวต้องตัดบรรทัดได้

ร่างค่าใช้จ่ายและ Court Day มีระบบร่างเดิมแล้ว ร่างงาน/รับเรื่องให้เพิ่มเฉพาะการเก็บช่องที่กำลังกรอก แยกสำนักงานและผู้ใช้ ยังไม่เสนอ sync ทุกข้อมูลอัตโนมัติ เมื่อบันทึกล้มเหลวต้องคงข้อความและไฟล์ที่ยังไม่ส่ง ถ้าตัวงานบันทึกแล้วแต่ไฟล์ล้มเหลว ให้ส่งไฟล์ต่อด้วย ID เดิม

## สัญญา API ที่ใช้ได้อยู่แล้ว

| การทำงาน | คำขอเดิม | ข้อกำหนด |
| --- | --- | --- |
| เปิดงาน | `GET /tasks/:taskId` | คดี ผล ไฟล์ ประวัติตามสิทธิ์; เปิดจากรายการ/แจ้งเตือนด้วย task ID |
| รับงาน | `POST /tasks/:taskId/acknowledge` | แสดงเฉพาะงานที่รับได้; เปลี่ยนสถานะรับงานหลังคำขอสำเร็จ |
| ทำวันนี้ | `POST /tasks/:taskId/confirm-plan` | `{ date: 'YYYY-MM-DD' }` คำนวณวัน Asia/Bangkok |
| บันทึกสั้น | `POST /tasks/:taskId/comments` | `{ body }`; คงข้อความเมื่อส่งไม่สำเร็จ |
| รายงานประจำวัน | `POST /tasks/:taskId/daily-update` | `completed`, `remaining` บังคับ, `blocker` เสริม; กางเป็นข้อมูลเพิ่มเติม ไม่ส่งข้อความช่องเดียวแทนทั้งสองช่อง |
| ไฟล์ | upload/download ใน `apps/mobile/src/api/files.ts` | แนบให้ task เดิม; retry เฉพาะไฟล์ที่เหลือ |
| เพิ่ม/แก้งานในคดี | `POST /cases/:caseId/tasks`, `PATCH /cases/:caseId/tasks/:taskId` | ส่ง assignee ID ของตัวเองให้ชัดเมื่อใช้ค่าเริ่มต้น; เว้น dueDate หากไม่ระบุ |
| งานทั่วไป | `GET/POST /todos`, `PATCH /todos/:taskId` | `view=mine|created|review` ต้องนำ implementation อีก worktree มาเทียบและรวม; controller ปัจจุบันยังไม่รับ query นี้ |
| ส่งตรวจในคดี | `PATCH /cases/:caseId/tasks/:taskId/handoff` | ผู้ตรวจ/สิทธิ์ตาม API; ผู้ส่งยังมีรายการส่งตรวจหลังโอน |
| ตรวจในคดี | `POST /cases/:caseId/tasks/:taskId/accept`, `/reject` | ดูผลและไฟล์ก่อนตรวจ; reject มี reason; ไม่ใช้ checkbox/สถานะ DONE แทนการตรวจ |
| ส่งตรวจ/ตรวจงานทั่วไป | `/todos/:taskId/handoff`, `/accept`, `/reject` | handoff ใช้ PATCH, accept/reject ใช้ POST; ผู้ตรวจเป็นคนอื่นและมีสิทธิ์ |
| SOP | `GET /practice-setup/playbooks` | รุ่นล่าสุดต่อชุด; รุ่นเดิมที่ผูกคดีเปิดอ่านได้ |
| ตรวจ SOP / สร้างงาน | `POST /practice-setup/cases/:caseId/preview`, `/apply` | `{ releaseId }`; preview สำเร็จก่อนยืนยัน อ่าน existing เพื่อแสดงว่าใช้แล้ว; รักษาการป้องกันซ้ำของ API |

ปุ่มในแอปจริงต้องยึดสิทธิ์ API และจัดการ 403/404 การสลับบทบาทในต้นแบบใช้ทบทวนหน้าจอ ไม่ใช่ระบบ authentication หรือหลักฐานสิทธิ์

## งานที่เหมาะกับเว็บต่อ

แก้/เผยแพร่ SOP หลายขั้นตอน ตั้งค่าประเภทคดี/บทบาท เอกสารยาว รายงานเชิงวิเคราะห์ การเงิน และ audit ใช้เว็บ มือถือใช้เปิดอ่าน ดำเนินงาน และเก็บข้อมูลหน้างาน

## ตรวจรับเมื่อพัฒนา native

- คงแท็บเดิมทั้งห้า สีและรูปแบบการ์ดเดิม ทดสอบทั้ง 4 roles และกรณีผู้ใช้สลับสำนักงาน
- หน้า Owner คงกำลังคน/วันลา งานครบกำหนด นัดสำนักงาน ชุดเบิก/ยอด สถิติคดี งานเกินกำหนด คำเตือน และทางลัด; เลขสรุปกับรายการปลายทางต้องมาจากข้อมูลชุดเดียวกัน ปุ่มของแต่ละคนเปิดงานของคนนั้น
- Owner/Senior เห็นคิวตรวจเฉพาะที่ทำรายการได้ Lawyer/Assistant ไม่มีปุ่มอนุมัติทั่วไป; ตรวจข้อยกเว้น Lead/ผู้ตรวจตาม API
- ผู้ช่วยไม่เห็นคดีที่ไม่ได้รับมอบหมาย; Senior ไม่เห็นข้อมูลอนุมัติการเงิน/ตั้งค่าสำนักงานแบบ Owner
- เปิดจากวันนี้ รายการ และแจ้งเตือนถึง task ID เดียวกัน ไม่วนไปหน้าแก้ไขคดี
- สร้างงานชื่อเดียวได้ ผู้รับผิดชอบเป็นตัวเอง วันส่งว่าง; เปลี่ยนคน/เติมข้อมูลเสริมได้ครบ
- ถ้าต้องตรวจ ต้องเลือกผู้ตรวจอื่นที่มีสิทธิ์ งานรอตรวจไม่มีช่องติ๊ก/สถานะ DONE ข้ามการตรวจ
- รับงาน → วางแผน → บันทึก/แนบผล → ส่งตรวจ → ส่งกลับพร้อมเหตุผล → แก้/ส่งใหม่ → ตรวจผ่านครบ และผู้ส่งยังเห็นงาน
- เปิดวิธีทำของงานได้ ใช้ SOP ต้องตรวจรายการก่อน retry/กดซ้ำไม่เพิ่มงานซ้ำ
- คนใหม่ได้รับ routine ตัวอย่างแล้วเปิดไฟล์ต้นทาง แนบผล ตรวจรายการ และส่งถึงผู้ตรวจได้ใน task เดิม; ผลไม่ครบ/ยังติดขัดแจ้งวิธีแก้และไม่ส่งตรวจ งานทั่วไปไม่โดนเงื่อนไข routine ย้อนหลัง
- ผู้มีสิทธิ์ดูแลงานเห็น completed/remaining/blocker และเวลาอัปเดตจาก task เดิม; Owner เทียบคนจากวันที่ถูกต้อง แยกคิวทำ/ตรวจ ข้อมูลวันก่อน/ไม่มีรายงาน/โหลดไม่ได้ต้องไม่กลายเป็นสัญญาณว่าใครว่าง
- Reviewer ต้องเป็นคนอื่นจากผู้รับงาน; ผู้สร้างอาจเป็นผู้ตรวจของงานที่มอบหมายให้คนอื่นได้เมื่อ API อนุญาต
- บริษัทชื่อเดียวบันทึกได้ เบอร์/อีเมลผิดหรือไม่มีชื่อบุคคลต้องแจ้งตรงช่องและคงข้อมูลอื่น
- clientId จากหน้าลูกค้าต้องผูกลูกค้ารายเดิม หากโหลดไม่ได้แจ้งก่อนสร้างเป็นเรื่องไม่มีลูกค้า
- ใช้ schema ประเภทเรื่องเดียวกับเว็บ/API ข้อหาคดีอาญายังบังคับแม้ฟอร์มสั้น
- เน็ตหลุด ต่ออายุ token ไฟล์ส่งไม่ครบไม่ล้างร่าง/สร้างงานซ้ำ ร่างไม่ปะปนผู้ใช้/สำนักงาน
- ตรวจ iOS/Android จริง: คีย์บอร์ด ฟอนต์ใหญ่ กล้อง สิทธิ์ไฟล์ push; browser prototype ไม่ใช่ native E2E

## ผลตรวจต้นแบบ

- รอบงานประจำและการมอบหมาย: หน้าเทียบคนของ Owner และหน้าทำงานผู้ช่วยที่ 375 × 812 ไม่มี horizontal overflow; แถบสลับบทบาทของต้นแบบอยู่ในจอครบ
- Owner เลือกคนจากคิวค้าง คิวตรวจ งานวันนี้/เสร็จวันนี้ จุดติดขัด เวลาอัปเดต นัดและวันลาได้ การไม่มีงานหรือไม่มีรายงานไม่ถูกตีความว่าว่าง; เลือกคนแล้วคงข้อมูลร่าง และการมอบหมายที่มีข้อขัดแย้งต้องยืนยันคำเตือนก่อนบันทึก
- ตรวจ flow งานประจำ: รับงาน → แจ้งเอกสารขาด → Owner เห็นจุดติดขัด → แก้ข้อขัดข้อง → เปิดต้นฉบับ/แนบ/ตรวจรายการ → ส่ง Senior → ส่งกลับพร้อมเหตุผล → ตรวจใหม่/ส่งใหม่ → ตรวจผ่านได้ครบ; ส่งก่อนผลครบถูกปฏิเสธพร้อมบอกสิ่งที่ขาด ผู้ช่วยไม่มีปุ่มอนุมัติ และ Owner สร้างงานประจำให้ทนายแล้วส่งตรวจได้
- Self-check ครอบคลุมการแยกคิวทำงานกับคิวตรวจ รายงานที่ยังไม่ครบ กรณีไม่มีงาน และความพร้อมส่งงานประจำผ่านด้วย `node docs/design/mobile-work-prototype/check.cjs`; ผลข้างต้นเป็นข้อมูลและ interaction ของต้นแบบ ยังไม่ได้เชื่อม API หรือบันทึกขั้นตอน SOP ลงฐานข้อมูล
- JavaScript syntax ผ่าน
- รอบปรับ Owner: จอ 375 × 812 ไม่มี horizontal overflow และคง 5 แท็บ; เจ้าของยังเห็นทุกส่วนเดิมเมื่อ URL เป็น variant C
- กดรอฉันตรวจ → เปิดงาน/ผล/ไฟล์ → ตรวจผ่าน → จำนวนรอตรวจลดลง; กดรายชื่อคุณพิมแล้วเห็นเฉพาะงานคุณพิม; ชุดเบิกรออนุมัติ 2 ชุด/2,250 บาท และรอจ่าย 1 ชุด/1,200 บาทเปิดรายการกับรายละเอียดตรงสถานะ
- Owner controls ไม่แสดงในหน้า Senior/ทนาย/ผู้ช่วย; ทั้ง 4 roles คงแท็บเดิม การตรวจรอบนี้เป็น browser prototype ไม่ใช่ native/API
- ตรวจซ้ำด้วย `node docs/design/mobile-work-prototype/check.cjs`: ส่วนเดิม ตัวกรองรายคน ตัวเลขเมื่อปิดงาน วันลาทับงาน และตัวกรองชุดเบิกผ่าน; `git diff --check` ผ่าน
- บทบาทอื่นสลับ A/B/C ได้; Owner คงภาพรวมหน้าเดิมทุก variant เพื่อไม่แทนหน้าเดิมด้วย Court Day หรือแฟ้มคดี
- ตรวจทั้ง 4 roles ใน browser 670 พิกเซลและกรอบมือถือ 410 พิกเซล ไม่มี horizontal overflow; ทุก role คงแท็บเดิม 5 แท็บ
- Owner/Senior มีทางเข้าตรวจงาน Lawyer/Assistant ไม่มีทางเข้าตรวจทั่วไป ผู้ช่วยเห็นแฟ้มตัวอย่างที่ได้รับมอบหมายเท่านั้น
- กด flow ตัวอย่าง ผู้ช่วยรับงาน → ทำวันนี้ → บันทึก/แนบผล → ส่ง Senior → ส่งกลับพร้อมเหตุผล → แนบเพิ่ม/ส่งใหม่ → ตรวจผ่าน → ผู้ส่งยังเห็นใน “ส่งตรวจแล้ว” ได้ครบ
- การส่งกลับโดยไม่กรอกเหตุผลถูกปฏิเสธ ผู้ช่วยไม่มีปุ่มตรวจผ่านในงานที่ส่งแล้ว
- สร้างงานจากชื่ออย่างเดียวได้ โดยเป็นงานของตัวเองและไม่บังคับวันส่ง; ชื่อว่าง/ช่องว่างถูกปฏิเสธ จำลองบันทึกล้มเหลวแล้วยังคงชื่อไว้และลองใหม่ได้
- ตัวเลือกผู้รับผิดชอบในฟอร์มแยกตามลำดับบทบาท ผู้ตรวจไม่รวมตัวเอง ผลนี้เป็นการทดสอบ interaction ของต้นแบบ ไม่ใช่การตรวจสิทธิ์ API/native รอบใหม่
- ภาพเป็น browser prototype ข้อมูลตัวอย่าง ยังไม่ได้ติดตั้ง native build หรือทดสอบกล้อง/push จริง
